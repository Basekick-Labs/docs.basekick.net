Track every significant operation in your Arc deployment. Audit logging captures permission refusals, token and RBAC changes, data access, configuration changes, and infrastructure events for compliance and security monitoring.

## Overview

Arc Enterprise audit logging provides:

- **Comprehensive event capture** — Permission refusals, data operations, token and RBAC changes, and infrastructure events
- **Query and filter API** — Search logs by event type, actor, database, and time range
- **Configurable retention** — Automatic cleanup of old audit entries
- **Non-blocking** — Audit events are captured asynchronously with zero impact on request latency

## Event types

| Category | Events | Description |
|----------|--------|-------------|
| **Permission refusals** | `auth.failed` | A request answered 401 or 403 that reaches the audit log: mostly a valid token without the permission a route needs, or a refused cluster cache-invalidation signature (actor `anonymous`) |
| **Token management** | `token.created`, `token.updated`, `token.rotated`, `token.revoked`, `token.deleted`, `token.team_added`, `token.team_removed` | API token lifecycle and team membership changes |
| **RBAC** | `rbac.org.created`, `rbac.team.updated`, `rbac.role.deleted`, etc. | Organization, team, role, and measurement permission changes |
| **Data Operations** | `data.query`, `data.write`, `data.import`, `data.delete` | Data read/write operations |
| **Database Management** | `database.created`, `database.deleted` | Database lifecycle events |
| **Infrastructure** | `mqtt.*`, `compaction.*`, `tiering.*` | System and background operations |
| **API** | `api.post`, `api.put`, `api.delete` | Catch-all for other API operations |

Action names are lowercase, because they are built from the HTTP method with
`strings.ToLower` — `api.post`, not `api.POST`. A log query using the
uppercase form matches nothing.

From v27.01.1 the compaction prefix follows its neighbours instead of
reporting every request as a trigger. `POST /api/v1/compaction/trigger` keeps
the action `compaction.triggered`; the read routes carry `compaction.get`, and
`compaction.head` for the HEAD requests Arc registers alongside every GET. A
`POST` to a read route, which Arc answers with 405, is `compaction.post`.
Before that release all of them were recorded as `compaction.triggered`, so
anyone counting that action for alerting was over-counting and the number will
drop after upgrading.

From v27.01.1, `include_reads` covers `HEAD` and `OPTIONS` as well as `GET`:
at the default `include_reads = false` none of the three is recorded, so the
`compaction.head` action appears only with `include_reads = true`. Before that
release, `HEAD` and `OPTIONS` requests were recorded at the default setting,
and a monitoring probe that polled with `HEAD` wrote one row per poll.

From v27.01.1, an event for a request that ended in an error (for example a
`404` for an unknown ID, a `405`, or a `500`) records that status in
`status_code`. Earlier versions recorded `200`. The event type names the
request, not its outcome: a refused token revoke is still `token.revoked`,
with `status_code` `409`. Check `status_code` before reading an event as a
change that took effect.

## Token and RBAC changes

Before v27.01.1, no change made through `/api/v1/auth/tokens` or
`/api/v1/rbac` was recorded, on any version since audit logging shipped: those
routes ran ahead of the audit middleware. Since v27.01.1 they are recorded,
with the token name as the actor. Changes made before the upgrade were not
recorded and cannot be recovered.

| Request | Event |
|---|---|
| `POST /api/v1/auth/tokens` | `token.created` |
| `PATCH /api/v1/auth/tokens/:id` | `token.updated` |
| `POST /api/v1/auth/tokens/:id/rotate` | `token.rotated` |
| `POST /api/v1/auth/tokens/:id/revoke` | `token.revoked` |
| `DELETE /api/v1/auth/tokens/:id` | `token.deleted` |
| `POST /api/v1/auth/tokens/:id/teams` | `token.team_added` |
| `DELETE /api/v1/auth/tokens/:id/teams/:team_id` | `token.team_removed` |
| `POST /api/v1/rbac/...` | `rbac.<resource>.created` |
| `PATCH /api/v1/rbac/...` | `rbac.<resource>.updated` |
| `DELETE /api/v1/rbac/...` | `rbac.<resource>.deleted` |

`<resource>` is named after the last resource segment of the path, which is
the thing the route changes: `org` for `organizations`, `team` for `teams`,
`role` for `roles`, and `measurement_permission` for `measurements` and
`measurement-permissions`. So `POST /api/v1/rbac/organizations/:org_id/teams`
is `rbac.team.created`, `POST /api/v1/rbac/teams/:team_id/roles` is
`rbac.role.created`, and `POST /api/v1/rbac/roles/:role_id/measurements` is
`rbac.measurement_permission.created`.

Token and RBAC reads are recorded only with `include_reads = true`: RBAC reads
as `rbac.<resource>.read`, token reads as `api.get` (`api.head`, `api.options`).

On a cluster, a write to a token that exists only on one node acts on that
node only (see
[Node-local tokens on a cluster](/arc/configuration/authentication/#node-local-tokens-on-a-cluster-enterprise)).
Its event carries a `detail` with `scope` (`node`), `node_id`, `token_id` and
`token_name`. A refusal of such a write records its `code` in `detail`, with
`node_id` and `token_id` when known:

```json
{
  "event_type": "token.revoked",
  "actor": "admin",
  "method": "POST",
  "path": "/api/v1/auth/tokens/7/revoke",
  "status_code": 200,
  "detail": "{\"node_id\":\"<node_id>\",\"scope\":\"node\",\"token_id\":\"7\",\"token_name\":\"legacy-ci\"}"
}
```

## What is recorded and what is not

- **Refusals after authentication:** any request that reaches the audit log
  and is answered `401` or `403` is recorded as `auth.failed`. Mostly this is
  a valid token that lacks the permission or license feature a route needs,
  with the token name as the actor.
- **Authentication failures are not recorded:** a request to an
  authenticated route with no token or an invalid one is refused (`401`) by
  authentication before it reaches the audit log.
- **Never recorded, in any method:** `/health`, `/healthz`, `/metrics`,
  `/api/v1/ready`, `/api/v1/logs`, and since v27.01.1 `/api/v1/auth/verify`,
  even with `include_reads = true`.
- **Public routes:** a write (`POST`, `PUT`, `PATCH`, `DELETE`) to a public
  route runs ahead of authentication and is recorded with the actor
  `anonymous`. In practice this is mainly `POST /api/v1/internal/cache/invalidate`,
  the signed cache invalidation that cluster peers send after a compaction:
  one row per call, and a refused signature (`403`) is `auth.failed`.

## Configuration

### TOML

```toml
[audit_log]
enabled = true
retention_days = 90          # Auto-cleanup entries older than this
include_reads = false        # Also log GET, HEAD and OPTIONS requests (high volume)
```

### Environment variables

```bash
ARC_AUDIT_LOG_ENABLED=true
ARC_AUDIT_LOG_RETENTION_DAYS=90
ARC_AUDIT_LOG_INCLUDE_READS=false
```

<Callout type="warn" title="High-volume read logging">
Enabling `include_reads` logs every `GET`, `HEAD` and `OPTIONS` request. This can generate significant log volume in high-throughput environments. Enable it only when needed for compliance or debugging, and consider a shorter `retention_days` when active.
</Callout>

## API reference

All audit endpoints require admin authentication.

### Query audit logs

```bash
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?limit=20"
```

**Filter parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `event_type` | string | Exact event type (e.g., `auth.failed`, `data.write`); a prefix such as `rbac` matches nothing |
| `actor` | string | Exact actor: a token name, or `anonymous` |
| `database` | string | Filter by database name |
| `since` | string | Start time (RFC3339, e.g., `2026-02-01T00:00:00Z`) |
| `until` | string | End time (RFC3339) |
| `limit` | int | Maximum results (default: 100, at most 10000) |
| `offset` | int | Pagination offset |

**Examples:**

```bash
# Refusals after authentication (401/403) since a given time
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?event_type=auth.failed&since=2026-02-12T00:00:00Z"

# All write operations to the production database
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?event_type=data.write&database=production"

# Recent role grants
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?event_type=rbac.role.created&limit=50"

# Token revocations
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?event_type=token.revoked"

# Activity by a specific token
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/logs?actor=telegraf-writer&limit=100"
```

**Response:**

```json
{
  "success": true,
  "data": [
    {
      "id": 1542,
      "timestamp": "2026-02-13T10:30:00Z",
      "event_type": "data.write",
      "actor": "telegraf-writer",
      "method": "POST",
      "path": "/api/v1/write/msgpack",
      "database": "production",
      "status_code": 204,
      "ip_address": "10.0.1.50",
      "user_agent": "Telegraf/1.30.0",
      "duration_ms": 3
    },
    {
      "id": 1541,
      "timestamp": "2026-02-13T10:29:55Z",
      "event_type": "auth.failed",
      "actor": "dashboard-reader",
      "method": "DELETE",
      "path": "/api/v1/auth/tokens/12",
      "status_code": 403,
      "ip_address": "192.168.1.100",
      "user_agent": "curl/8.5.0",
      "duration_ms": 0
    }
  ],
  "count": 2
}
```

### Get audit statistics

Aggregate event counts by type, useful for dashboards and alerting.

```bash
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/stats"
```

Counts cover the last 24 hours unless `since` (RFC3339) sets the start; there
is no end bound.

```bash
curl -H "Authorization: Bearer $ARC_TOKEN" \
  "http://localhost:8000/api/v1/audit/stats?since=2026-02-01T00:00:00Z"
```

**Response:**

```json
{
  "success": true,
  "data": {
    "auth.failed": 23,
    "data.write": 15420,
    "data.query": 8340,
    "token.created": 5,
    "rbac.role.created": 3,
    "database.created": 2
  },
  "since": "2026-02-01T00:00:00Z"
}
```

## Compliance use cases

### SOC 2

SOC 2 requires logging of access to systems and data. Arc audit logging captures:
- Who accessed the system (actor/token identification)
- What they did (event type and detail)
- When it happened (timestamp)
- Where the request came from (IP address)

### HIPAA

For healthcare data, enable `include_reads = true` to log all data access, including queries. Set `retention_days` according to your HIPAA retention requirements (typically 6 years).

### Security monitoring

Monitor `auth.failed` events to detect tokens calling routes they are not allowed to use. Requests with a missing or invalid token are refused before the audit log and are not recorded. Monitor the `token.` and `rbac.` event types listed in [Token and RBAC changes](#token-and-rbac-changes). `event_type` is an exact match, so query each type, or use `/api/v1/audit/stats`.

## Best practices

1. **Start with writes only** — Keep `include_reads = false` (default) and enable read logging only when compliance requires it.

2. **Set appropriate retention** — 90 days is a good default. Adjust based on your compliance requirements (HIPAA may require years).

3. **Monitor permission refusals and admin changes** — Set up alerts on `auth.failed` events. Monitor the `token.` and `rbac.` event types listed in [Token and RBAC changes](#token-and-rbac-changes). `event_type` is an exact match, so query each type, or use `/api/v1/audit/stats`.

4. **Pair with RBAC** — Use audit logs to verify that RBAC permissions are configured correctly by reviewing who accessed what data.

5. **Export for long-term analysis** — For retention beyond what Arc stores, periodically export audit logs to your SIEM or log management system.
