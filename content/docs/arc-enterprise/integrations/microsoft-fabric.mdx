Get Arc data into a Power BI report in Microsoft Fabric, entirely in the browser: no Power BI Desktop, no Windows machine, no gateway and nothing to install on Arc.

Two routes:

- **A notebook (any Arc since v25.12.1).** Steps 1–7 below.
- **Zero-copy through Iceberg (Arc 27.01.1, S3 storage).** Fabric reads Arc's Parquet files where they are, through a OneLake shortcut. See [Zero-copy: Iceberg through OneLake](#zero-copy-iceberg-through-onelake).

In the notebook route, a Fabric notebook queries Arc's HTTP API, receives the result as Arrow, and writes it to a Lakehouse table. Power BI reads that table directly (Direct Lake), and a schedule keeps it current.

```text
Arc  ──POST /api/v1/query/arrow──▶  Fabric notebook  ──▶  Lakehouse table  ──▶  Semantic model  ──▶  Power BI report
       (Arrow, over HTTPS)          (scheduled)          (Delta, OneLake)      (Direct Lake)
```

<Callout type="info" title="Works with the Arc you run today">
The Arrow endpoint used here is in every Arc release since v25.12.1. For older releases, use the JSON variant [below](#older-arc-releases-json).
</Callout>

## Before you start

- **A Fabric workspace on a trial or Fabric capacity.** Notebooks and Lakehouses are not available on a Power BI Pro–only workspace.
- **Arc reachable from the internet over HTTPS.** The notebook runs in Microsoft's cloud, so it cannot reach an Arc on your laptop or private network.
- **A read-only Arc token**, limited to the databases the report needs. Never use an admin token here.

The steps use the demo dataset `weather_tracking.weather_observations` (three cities, a reading every few minutes). Replace it with your own database and measurement.

## 1. Create a workspace

In [app.fabric.microsoft.com](https://app.fabric.microsoft.com), open **Workspaces → New workspace**, name it, and under **Advanced** choose **Trial** (or a Fabric capacity) as the license mode. You can check the mode later under **Workspace settings → Workspace type**:

![Workspace settings showing the workspace type Fabric Trial](/img/arc-fabric/arc-fabric-new-workspace.webp)

## 2. Create a Lakehouse

In the workspace, click **New item → Lakehouse**, name it `arc_lakehouse` and click **Create**:

![The New Lakehouse dialog with the name arc_lakehouse and Lakehouse schemas ticked](/img/arc-fabric/arc-fabric-new-lakehouse.webp)

The Lakehouse opens empty. With **Lakehouse schemas** on (the default), tables go in the `dbo` schema. **New semantic model** stays greyed out until the Lakehouse has a table:

![The empty Lakehouse: Tables with an empty dbo schema, and Files](/img/arc-fabric/arc-fabric-empty-lakehouse.webp)

## 3. Create a notebook

From the workspace, click **New item → Notebook**, then attach the Lakehouse in the notebook's Explorer with **Add data items**. (Opening the notebook from the Lakehouse attaches it for you.) Rename it `arc_to_lakehouse`:

![An empty notebook with arc_lakehouse attached in the Explorer](/img/arc-fabric/arc-fabric-notebook-attached.webp)

## 4. Pull data from Arc

Use two cells, so the token is never visible in the code you share or screenshot.

**Cell 1, the token.** Collapse it afterwards (**⋯ → Hide input**):

```python
ARC_TOKEN = "<a read-only Arc token>"
```

**Cell 2, the query:**

```python
import requests, pyarrow.ipc as ipc

ARC_URL = "https://arc.example.com"
SQL = """
SELECT * FROM weather_tracking.weather_observations
WHERE time > now() - INTERVAL 30 DAY
"""

r = requests.post(f"{ARC_URL}/api/v1/query/arrow",
                  headers={"Authorization": f"Bearer {ARC_TOKEN}"},
                  json={"sql": SQL}, stream=True, timeout=300)
r.raise_for_status()
table = ipc.open_stream(r.raw).read_all()   # Arrow: columnar, exact types
print(f"{table.num_rows} rows from Arc")

spark.createDataFrame(table.to_pandas()) \
     .write.mode("overwrite").saveAsTable("weather_observations")
```

Click **Run all**. The cell prints the row count and writes the table:

![The notebook after a run: the token cell hidden, the query cell, Spark jobs succeeded and 12762 rows from Arc, and the weather_observations table with its columns in the Explorer](/img/arc-fabric/arc-fabric-notebook-run.webp)

<Callout type="info" title="Refresh the Explorer">
The new table appears in the Explorer only after a refresh: **dbo → ⋯ → Refresh**.
</Callout>

The `WHERE time > now() - INTERVAL 30 DAY` filter keeps each run bounded: the whole result passes through the notebook's memory, so pull the window the report needs rather than the whole measurement. Any SQL Arc accepts works here, including aggregations, so you can also ship pre-aggregated data (for example hourly averages) instead of raw rows.

## 5. Create the semantic model

Back in the Lakehouse, click **New semantic model**, name it, and select `dbo → weather_observations`:

![The New semantic model dialog: Direct Lake semantic model named weather, workspace Arc Demo, dbo.weather_observations selected](/img/arc-fabric/arc-fabric-semantic-model.webp)

The model uses **Direct Lake**: Power BI reads the table's files in OneLake directly, with no import step.

## 6. Build the report

From the semantic model, create a new report. For a temperature chart per city:

- **Line chart**: `time` on the X-axis, `temperature` on the Y-axis, `city` in the Legend.
- Set the Y-axis field to **Average**. Power BI defaults numeric fields to Sum, which adds up readings that share a timestamp.
- Filter by city in the **Filters** pane, or add a **Slicer** on `city`.

![The Power BI report editor: Average of temperature by time and city for Buenos Aires, London and Tokyo, with a city filter showing 4254 rows per city](/img/arc-fabric/arc-fabric-report-edit.webp)

Save the report. In reading view:

![The saved report Weather in three cities in reading view](/img/arc-fabric/arc-fabric-report-view.webp)

## 7. Schedule the refresh

In the notebook, open **Settings (⚙) → Schedule → Add schedule**, choose **Hourly** with an interval of 1, and **Save**:

![The notebook schedule panel: repeat hourly, every 1 hour, with start and end dates and time zone](/img/arc-fabric/arc-fabric-schedule.webp)

Each run replaces the table with the latest window from Arc. An open report does not pick up the new data on its own: click **Refresh** in the report to see it.

## Zero-copy: Iceberg through OneLake

With Arc 27.01.1 on S3 storage, Fabric can read Arc's own Parquet files in place: Arc publishes each measurement as an Iceberg table, a OneLake shortcut points at it, and Fabric presents it as a Lakehouse table. No notebook, no copy, no schedule.

```text
Arc  ──Parquet + Iceberg metadata──▶  S3 bucket  ◀──shortcut──  Lakehouse table  ──▶  Semantic model  ──▶  Power BI report
                                                     (OneLake, Iceberg → Delta)       (Direct Lake on SQL)
```

**Requirements:**

- Arc 27.01.1 or later with an S3 primary (`storage.backend = "s3"`).
- [Iceberg export](/arc/integrations/apache-iceberg/) on, with the **colocated** layout and the warehouse at the storage root (the default):

  ```toml
  [iceberg]
  enabled = true
  layout  = "colocated"
  ```

  The default `warehouse` layout does not work here: OneLake converts the table, then Fabric fails reading the first data file, because the data is outside the shortcut's folder. Tables created before you set the layout keep their old location; see [Table layout](/arc/integrations/apache-iceberg/#table-layout) to move one.
- An AWS access key that can only read the bucket (`s3:ListBucket` and `s3:GetObject`).
- A Lakehouse created with **Lakehouse schemas** unticked.

### 1. Create the shortcut

In the Lakehouse, open **Tables → ⋯ → New shortcut → Amazon S3**, and create a connection with the bucket URL (`https://<bucket>.s3.<region>.amazonaws.com`) and the read-only key. Then expand the bucket and tick the **measurement's folder**, `<database>/<measurement>`. Fabric recognises it as a table:

![The New shortcut dialog: the bucket expanded to energy_grid, with the fuel_daily table ticked](/img/arc-fabric/arc-fabric-iceberg-shortcut-select.webp)

Click **Next**, then **Create**:

![The shortcut summary: target type AmazonS3, location arc_iceberg > Tables, shortcut fuel_daily](/img/arc-fabric/arc-fabric-iceberg-shortcut-create.webp)

Pick the bucket's region close to your Fabric capacity: every read crosses from S3 to Fabric.

### 2. Check the table

The table appears under **Tables** with Arc's columns. Its preview reads Arc's files directly:

![The Lakehouse preview of fuel_daily: solar, coal, total, region, nuclear, wind, region_name, time, gas and renewables](/img/arc-fabric/arc-fabric-iceberg-preview.webp)

On our test dataset (`energy_grid.fuel_daily`, 38,360 daily rows from 2019 to mid-2026 in 2,740 files) the SQL endpoint's `SELECT COUNT(*)` matched Arc's count.

### 3. Semantic model and report

Click **New semantic model** and choose **Direct Lake on SQL**:

![The New semantic model dialog with Direct Lake on SQL selected and fuel_daily ticked](/img/arc-fabric/arc-fabric-iceberg-semantic-model.webp)

<Callout type="warn" title="Direct Lake on OneLake and long histories">
Direct Lake has a per-table limit on the number of files, which depends on the capacity. Arc writes at least one file per hour that has data, so a long history passes it quickly: our 2,740-file table did on a trial capacity. **Direct Lake on OneLake** has no fallback and the model fails to load. **Direct Lake on SQL** falls back to DirectQuery and keeps working.
</Callout>

Build the report as in [step 6](#6-build-the-report):

![A Power BI report on fuel_daily: generation by fuel from 2019 to 2026, with a region slicer](/img/arc-fabric/arc-fabric-iceberg-report.webp)

### Keeping it current

Arc commits a new snapshot on each reconcile pass that finds changed files (`iceberg.reconcile_interval`, 300 seconds by default), and OneLake converts the new snapshot when it detects it. There is nothing to schedule in Fabric.

<Callout type="warn" title="Never run orphan-file cleanup on these tables">
The table's folder is Arc's data folder. `remove_orphan_files` (from a Fabric Spark notebook or any other engine) deletes every file there that no snapshot references, including data Arc wrote since the last pass.
</Callout>

**Limits:**

- **Cold tier.** Files that tiering moves to a cold tier leave the table folder, and the shortcut cannot read them. Report on hot data, or use the notebook route.
- **Read only.** The shortcut is a view of Arc's data; write to Arc, not to the table.

## Older Arc releases (JSON)

Releases before v25.12.1 have no Arrow endpoint. Use the JSON one instead. JSON carries no column types, so convert the time column and check numeric types yourself: a float column whose values happen to be whole numbers comes back as integers.

```python
import requests, pandas as pd

r = requests.post(f"{ARC_URL}/api/v1/query",
                  headers={"Authorization": f"Bearer {ARC_TOKEN}"},
                  json={"sql": SQL}, timeout=300)
r.raise_for_status()
res = r.json()
pdf = pd.DataFrame(res["data"], columns=res["columns"])
pdf["time"] = pd.to_datetime(pdf["time"])

spark.createDataFrame(pdf).write.mode("overwrite").saveAsTable("weather_observations")
```

## Production notes

- **Keep the token out of the notebook.** For anything beyond a trial, store it in Azure Key Vault and read it at run time with `notebookutils.credentials.getSecret("https://<vault>.vault.azure.net/", "<secret-name>")`.
- **Least privilege.** The notebook's queries go through RBAC like any other: give the token read access to the databases (or measurements) the report uses, nothing more. Every run is recorded in the audit log when audit logging is on.
- **Governance row caps.** If the token has a governance policy with a row cap, a query that hits it returns the rows up to the cap, and Arc signals it in the `Arc-Rows-Capped` HTTP trailer, which this notebook does not read. Make sure the cap is above the window you pull, or the table will be silently incomplete.
- **Size the window.** Each run moves the whole query result. Bound it by time, or aggregate in SQL, to keep runs fast.
- **Failure alerts.** The schedule panel can email you when a scheduled run fails.
