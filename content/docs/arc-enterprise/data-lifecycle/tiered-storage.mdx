---
title: Tiered Storage
description: Age Arc Enterprise data from hot storage to S3 or Azure Blob Storage with per-database policies; cold files stay queryable in place, with no retrieval step.
---

Reduce storage costs with automatic hot/cold data tiering. Recent data stays on fast primary storage while older data moves to object storage that costs a fraction of block storage per gigabyte, and queries keep reading it in place.

## Overview

Arc Enterprise implements a 2-tier storage model:

```text
┌─────────────────────────────────────────────────────────────┐
│                    Arc Tiered Storage                        │
│                                                              │
│  HOT TIER (Local / Primary Storage Backend)                 │
│  ├── Recent data (configurable, default: 30 days)           │
│  ├── Optimized for low-latency queries                      │
│  └── Cost: $$$                                               │
│                                                              │
│           │ Automatic migration (age-based)                  │
│           ▼                                                  │
│                                                              │
│  COLD TIER (S3 / Azure Blob Storage)                        │
│  ├── Historical data (30+ days)                             │
│  ├── Optimized for cost efficiency                          │
│  └── Cost: $                                                 │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**Key features:**

- **Age-based migration** — Data older than a configurable threshold automatically moves to the cold tier
- **Per-database policies** — Override global defaults for specific databases
- **Hot-only databases** — Exclude specific databases from tiering entirely
- **Scheduled migrations** — Cron-based scheduler runs migrations automatically
- **Manual migrations** — Trigger migrations on-demand via API
- **Zero recompression** — Files move as-is with no re-encoding overhead
- **Transparent queries** — Queries automatically span both tiers

## Configuration

### Global settings

```toml
[tiered_storage]
enabled = true
migration_schedule = "0 2 * * *"     # Cron: run at 2am daily
migration_max_concurrent = 4          # Parallel file transfers
migration_batch_size = 100            # Files per migration batch
default_hot_max_age_days = 30         # Data older than this moves to cold
scan_timeout = "2h"                   # Budget for one tier scan
```

`scan_timeout` bounds **one** tier scan on every path that runs one: the scan at startup, `POST /api/v1/tiering/scan`, and the pre-migration scan inside a migration cycle or `POST /api/v1/tiering/migrate`. Before v27.01.1 the first two were capped at 30 minutes with no way to change it, while a cycle gave its scan the cycle's own 2 hours ([arc#1154](https://github.com/Basekick-Labs/arc/issues/1154)).

Inside a cycle the scan runs on a budget derived from the cycle's, so it gets whichever of the two is shorter and migration keeps the remainder. At the default the two are equal and the derivation changes nothing; setting `scan_timeout` above 2 hours is harmless because the cycle still bounds the scan.

Setting it **below** the time a full scan takes is harmful rather than conservative. Hot-row retirement runs only after the whole walk, so a scan that always truncates never retires a row for a file that has left hot storage — and a measurement whose remaining rows are all cold drops that node's local files from reads. Size it from how long a full scan takes on your storage root, which scales with the number of objects under it rather than their size. Zero, negative and malformed durations are refused at startup.

### Cold tier backend

<Tabs items={['AWS S3 / MinIO', 'Azure Blob Storage']}>

```toml
[tiered_storage.cold]
enabled = true
backend = "s3"
s3_bucket = "arc-archive"
s3_region = "us-east-1"
# s3_access_key = ""          # Use env: ARC_TIERED_STORAGE_COLD_S3_ACCESS_KEY
# s3_secret_key = ""          # Use env: ARC_TIERED_STORAGE_COLD_S3_SECRET_KEY
s3_use_ssl = true
s3_path_style = false
```

Cold objects are written with no storage class set, so they land in S3 Standard, and are queried in place. Arc has no storage-class setting, deliberately; see [Best practices](#best-practices). Keep bucket lifecycle rules off the cold prefix: a transition to `GLACIER` or `DEEP_ARCHIVE` makes those files unreadable to queries until restored.

```bash
# Global tiering settings
ARC_TIERED_STORAGE_ENABLED=true

ARC_TIERED_STORAGE_MIGRATION_BATCH_SIZE=100
ARC_TIERED_STORAGE_DEFAULT_HOT_MAX_AGE_DAYS=30

# Cold tier (S3)
ARC_TIERED_STORAGE_COLD_ENABLED=true
ARC_TIERED_STORAGE_COLD_BACKEND=s3
ARC_TIERED_STORAGE_COLD_S3_BUCKET=arc-archive
ARC_TIERED_STORAGE_COLD_S3_REGION=us-east-1
ARC_TIERED_STORAGE_COLD_S3_ACCESS_KEY=your_key
ARC_TIERED_STORAGE_COLD_S3_SECRET_KEY=your_secret
ARC_TIERED_STORAGE_COLD_S3_USE_SSL=true

# Cold tier (Azure)
ARC_TIERED_STORAGE_COLD_BACKEND=azure
ARC_TIERED_STORAGE_COLD_AZURE_CONTAINER=arc-archive
ARC_TIERED_STORAGE_COLD_AZURE_ACCOUNT_NAME=your_account
ARC_TIERED_STORAGE_COLD_AZURE_ACCOUNT_KEY=your_key
```

<Callout type="idea" title="Use Environment Variables for Secrets">
Store access keys and secret keys in environment variables rather than in `arc.toml`. This keeps secrets out of version control.
</Callout>

<Callout type="warn" title="An empty environment variable does not clear a value set in arc.toml">
Arc reads the environment through viper's `AutomaticEnv`, which treats an empty variable as unset. `ARC_TIERED_STORAGE_COLD_S3_ENDPOINT=""` therefore leaves whatever `s3_endpoint` the file sets in place — a cold tier meant for AWS silently keeps addressing that endpoint, every cold listing fails, and each migration cycle skips. To clear a key, remove it from the file or give the variable the value you actually want. The `arc.toml` shipped in the image set MinIO values (`localhost:9000`, static `minioadmin` keys, plain HTTP, path-style) under `[tiered_storage.cold]` through 26.09.2; since 26.09.3 those lines are commented out and Arc's built-in defaults apply — no endpoint, HTTPS, virtual-hosted addressing, credentials from the AWS chain. If you relied on the shipped MinIO values, uncomment that block as a set.
</Callout>

## Per-database policies

Override the global `default_hot_max_age_days` for specific databases, or exclude databases from tiering entirely.

### Create policy

```bash
curl -X POST http://localhost:8000/api/v1/tiering/policies \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "telemetry",
    "hot_max_age_days": 7
  }'
```

### Create hot-only policy

Exclude a database from tiering:

```bash
curl -X POST http://localhost:8000/api/v1/tiering/policies \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "database": "realtime",
    "hot_only": true
  }'
```

### List policies

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/tiering/policies
```

### Get policy

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/tiering/policies/telemetry
```

### Update policy

```bash
curl -X PUT http://localhost:8000/api/v1/tiering/policies/telemetry \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"hot_max_age_days": 14}'
```

### Delete policy

```bash
curl -X DELETE http://localhost:8000/api/v1/tiering/policies/telemetry \
  -H "Authorization: Bearer $TOKEN"
```

## API reference

All tiering endpoints require admin authentication.

### Get tiering status

```bash
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/tiering/status
```

**Response:**

```json
{
  "success": true,
  "data": {
    "enabled": true,
    "cold_backend": "s3",
    "default_hot_max_age_days": 30,
    "migration_schedule": "0 2 * * *",
    "last_migration": "2026-02-13T02:00:00Z"
  }
}
```

On a cluster node with peer file replication the status also carries `replication_events` — `{"applied", "dropped", "failed"}` — counting the tier rows this node wrote for files it did not ingest itself: files the replication puller pulled, and local copies removed because another node moved them to cold (since 26.09.3, see [Clusters and shared storage](#clusters-and-shared-storage)). `dropped` is zero on a healthy node; a non-zero `dropped` or `failed` means some rows wait for the next tier scan, which costs that node partition pruning until then. The field is absent on a node that has never received such a report.

### List files by tier

```bash
# All files
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8000/api/v1/tiering/files

# Filter by tier
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8000/api/v1/tiering/files?tier=cold"

# Filter by database
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8000/api/v1/tiering/files?database=telemetry&limit=50"
```

### Trigger manual migration

```bash
curl -X POST http://localhost:8000/api/v1/tiering/migrate \
  -H "Authorization: Bearer $TOKEN"
```

**Response:**

```json
{
  "success": true,
  "data": {
    "message": "Migration started",
    "files_eligible": 42
  }
}
```

On a cluster node that is not the primary writer the request is refused with `409 Conflict` naming the node's role; see [Clusters and shared storage](#clusters-and-shared-storage).

### Rescan tiers

```bash
curl -X POST http://localhost:8000/api/v1/tiering/scan \
  -H "Authorization: Bearer $TOKEN"
```

**Response:**

```json
{
  "files_scanned": 1590,
  "files_registered": 3,
  "files_skipped": 1587,
  "errors": 0,
  "cold_synced": 0,
  "hot_retired": 2,
  "hot_rows_written": 3
}
```

The scan brings the node's tier metadata in line with storage. Every migration cycle runs the same pass first, and since 26.09.3 every node runs it once at startup too, in the background, so files that arrived while the node was down — or were already on disk when upgrading — have rows as soon as the node is up; the log line `Startup tier scan completed` carries the same counts. It lists the hot tier and accounts for every hot file (`files_registered`; files whose row already says cold count as `files_skipped`), writing a row only where one is missing or out of date (`hot_rows_written`, zero on a node whose rows already match its disk), and it retires the rows of hot files that are no longer in hot storage (`hot_retired`) — what compaction leaves behind once it has consumed a measurement's raw files — after a five-minute grace period and a check that the file really is gone, so a file flushed or pulled while the scan runs is never retired. Cold rows are never touched. Without that retirement, a measurement whose files had all moved to cold kept an empty hot tier in every read, and a query without a time range on it returned no rows. In a cluster the scan also records the files other nodes moved to cold as `cold_synced`, and reports `"cold_sync_failed": true` when the cold tier could not be listed; see [Clusters and shared storage](#clusters-and-shared-storage).

#### When a scan runs out of its budget

A scan bounded by `scan_timeout` can stop part way, and from v27.01.1 it says so rather than looking like a clean pass ([arc#1154](https://github.com/Basekick-Labs/arc/issues/1154)). The rows it wrote before stopping are real; what it has **not** done is retire any stale hot row, because retirement runs only after the whole walk.

`POST /api/v1/tiering/scan` answers `503 Service Unavailable` with the counts it reached:

```json
{
  "error": "The tier scan ran out of its budget and stopped part way",
  "message": "The rows below were written, but the scan is incomplete and no stale hot rows were retired. Raise tiered_storage.scan_timeout above the time a full scan takes on this node.",
  "result": {
    "files_scanned": 25974,
    "files_registered": 25974,
    "files_skipped": 0,
    "errors": 0,
    "cold_synced": 0,
    "hot_retired": 0,
    "hot_rows_written": 25974,
    "truncated": true
  }
}
```

Before v27.01.1 the same case returned `500` with `context deadline exceeded` and no counts at all. A scan cancelled because the node is shutting down also answers `503`, with its own message — that one is not a budget problem and raising `scan_timeout` will not help it.

The **startup** scan has no response to carry any of this, so `GET /api/v1/tiering/status` reports the last scan this node ran:

```json
{
  "last_scan": {
    "files_scanned": 15738,
    "files_registered": 15738,
    "files_skipped": 0,
    "errors": 0,
    "cold_synced": 0,
    "hot_retired": 0,
    "hot_rows_written": 15738,
    "truncated": true
  },
  "last_scan_at": "2026-10-08T20:40:33.880463Z"
}
```

`"truncated": true` there means this node's tier rows are incomplete and no stale hot row was retired, which costs it partition pruning until a scan completes. Read it rather than calling the scan endpoint to find out, because calling that endpoint starts a scan.

#### Only one scan at a time

A second `POST /api/v1/tiering/scan` while one is running is refused with `409 Conflict` rather than starting a parallel scan:

```json
{
  "error": "A tier scan is already running on this node",
  "message": "Wait for it to finish and read its result from GET /api/v1/tiering/status, which reports the last scan."
}
```

The endpoint is synchronous and a scan over a large storage root can take a while, and Arc does not learn that a client disconnected — so without this an operator who gave up on a slow scan and retried would have started another full one over the same storage root, against the same metadata database, each invalidating the tier cache the query path reads. A scan inside a migration cycle is deliberately **not** refused: the cycle must scan before it migrates, or it would migrate from stale rows.

## Clusters and shared storage

How tiering behaves in a cluster depends on the [deployment pattern](/arc-enterprise/configuration/deployment-patterns/).

**Shared object storage (Pattern 2, `cluster.shared_storage_mode = true`).** The hot tier is the one bucket every node shares, so exactly one node moves files: migration runs on the Raft leader among the writers — the same primary-writer gate that retention and continuous queries use — and the gate is re-checked on every cycle, so a leader change takes effect at the next tick with no restart. Every other node, readers and the remaining writers alike, still runs a cycle on the same schedule, but only to bring its own tier metadata in line with storage: it lists the cold tier and records what the primary moved. Each node routes queries from its own metadata, so that sync is what keeps cold data in those nodes' query routing, and what stops a newly elected primary from re-migrating files its predecessor already moved.

Two consequences to plan for:

- All nodes fire on the same cron minute, so a non-primary learns a cycle's moves on its next cycle. Only a measurement's very first cold file is affected, and only for one cycle: once a node has any cold row for a measurement, its cold reads cover later moves. A node that restarts learns them at boot instead, from the startup tier scan (since 26.09.3), which on shared storage lists the shared hot bucket once per node per start — the same listing the nightly cycle already performs.
- The sync only ever adds or flips rows to cold. A cold row whose object has since disappeared from the cold tier is reported in a warning; the primary's reconciliation reverts such a row to hot when it finds the hot copy still present, so the file is migrated again rather than lost. A migration cycle requested while one is already running on the same node answers `409 Conflict` instead of overlapping it.

On a node that syncs but never migrates, `GET /api/v1/tiering/status` reports `"role_gated": true` under `scheduler`, and `POST /api/v1/tiering/migrate` answers `409 Conflict` with the node's role — retry it against the primary writer. `POST /api/v1/tiering/scan` runs the same sync on any node and reports how many rows it learned as `cold_synced`; see [Rescan tiers](#rescan-tiers).

A node in shared-storage mode must have `cluster.role` set to `writer`, `reader` or `compactor`. A node left at the default `standalone` refuses to start: it could win Raft leadership without ever passing the primary-writer gate, which would stop every singleton task on the cluster.

**Per-node local storage (Pattern 1).** A per-node cluster whose nodes keep each other in step with file replication (`cluster.replication_enabled = true`) is gated the same way: only the primary writer migrates, every node syncs its tier metadata from the cold tier each cycle, and every file the primary moves to cold is removed from the cluster file manifest before its hot copy goes — which is what unlinks the replica on every other node and stops replication from pulling it back. A per-node cluster without replication shares nothing and keeps migrating per node.

One requirement follows. **Every replicating node must run tiering with the same cold backend**: once the primary migrates a file, the only way a node can read it is through its own cold row and cold backend; a node with tiering off or no cold tier cannot see that data any more, and Arc says so at startup on such a node.

Since 26.09.3 a node's tier rows follow its own disk, not only what it ingested. A file the replication puller pulls is registered as hot the moment it lands, and when the primary moves a file to cold the node that removes its local copy confirms the object is in the cold tier before flipping its row to cold — so a measurement's first migrated file is readable on every node within seconds of the migration, not at the next cycle, and nothing needs tuning for it. Two counters show the path working: `tier_registered` beside `pulled` in `replication_catchup_status` on `/api/v1/cluster` (it tracks `pulled` where tiering is on, and stays at zero where it is not), and `replication_events` on `/api/v1/tiering/status`, whose `dropped` is zero on a healthy node.

<Callout type="warn" title="Before 26.09.3: a node's tier rows only described what it ingested">
On 26.09.2 and earlier, a node recorded tier rows only for files it flushed itself. Files pulled from a peer had no row until the next scan, and a file another node migrated was not marked cold locally until the next cold sync — at the default `0 2 * * *` schedule up to a day. Because the query layer routes reads from those rows, a node not currently ingesting a measurement lost partition pruning for it (`GET /api/v1/tiering/files` showed far fewer files on it than on the ingesting node), and a measurement with a cold row and no hot row dropped that node's local files from reads entirely: a windowed `count(*)` over data on its disk returned `0` with `success: true`. `POST /api/v1/tiering/scan` on each affected node closes the gap until the next migration cycle reopens it; upgrading removes it.
</Callout>

## Best practices

1. **Start with 30-day hot retention** — This is a good default for most workloads. Monitor query patterns and adjust based on how often historical data is accessed.

2. **Keep cold on S3 Standard or Azure Hot** — Arc writes cold objects with no storage class or access tier set, so on S3 they are Standard and on Azure they take the storage account's default tier, Hot unless the account owner changed it. Leave it that way. The saving tiering is built for is block storage versus object storage: a hot tier on EBS or local NVMe costs several times what S3 Standard does per gigabyte, and cold data stays queryable at object-store latency. Cold data in Arc is old telemetry you still query, not an archive you file away, so cheaper classes are a false economy: `STANDARD_IA` and `GLACIER_IR` add a per-gigabyte retrieval fee to every query that touches cold files, and `GLACIER`, `DEEP_ARCHIVE` and Azure Archive objects cannot be read at all without a restore. That is why Arc has no storage-class or access-tier setting. Do not attach a bucket lifecycle rule to the cold prefix that transitions objects out of Standard.

3. **Schedule migrations during off-peak hours** — The default `0 2 * * *` (2am daily) works well for most deployments.

4. **Use per-database policies for different retention needs** — Real-time dashboards may need 7-day hot data, while compliance databases may need 90 days.

5. **Mark real-time databases as hot-only** — Databases used exclusively for real-time dashboards should skip tiering so no query on them pays object-store latency.

6. **Use IAM roles or managed identity** — For cloud deployments, use IAM roles (AWS) or managed identity (Azure) instead of access keys.
