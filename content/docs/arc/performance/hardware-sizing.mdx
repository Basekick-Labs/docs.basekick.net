title: "Hardware Sizing"
description: "Measured starting points for native Arc OSS deployments, with MessagePack and line protocol ingestion, query workloads, and WAL enabled or disabled."
---

Choose a starting instance size from the workload you expect, then validate it
with your own schema, queries, retention period, and storage. Ingestion-only
capacity and the capacity available while queries run are different measurements.

**Scope:** ingestion measurements run for ten minutes with replayed, batched
data. Query-only measurements use 20 million unique rows. Combined measurements
grow from 20 million to approximately 81.5 million rows. These figures do not
establish capacity for days of continuous ingestion or billions of retained rows.

This guide covers a native, single-node Arc OSS deployment using an EBS-backed
local filesystem. The measurements use **Arc 26.09.3**, Ubuntu 24.04, and AWS EC2
instances in us-east-1. The campaign starts on Spot. After reclamations, servers
are replaced with the same instance types on-demand, preserving completed
cases and rerunning interrupted work. The run
date is **October 12, 2026**. Interrupted runs are excluded from capacity figures.

<Callout type="info" title="Use these as starting points">
These are measurements of the stated workload, with row reconciliation and
error checks. Validate your own schema, queries, retention, and longer operating
periods before adopting a sustained capacity target.
</Callout>

## Starting sizes

The following are **derived starting targets**, rounded down from half of the
validated WAL-enabled ingestion rates and half of the repeated query-only QPS.
They reserve workload headroom but have not been independently qualified as
continuous production rates. The columns describe separate ingestion-only and
query-only workloads; use the combined results when both will run together.

{/* begin:starting-table */}

| Instance | vCPU | RAM | MessagePack points/sec | Line protocol points/sec | Query-only QPS |
| --- | --- | --- | --- | --- | --- |
| m7i.xlarge | 4 | 16 GiB | 1.30M | 170.0k | 1.6 |
| m7i.2xlarge | 8 | 32 GiB | 1.30M | 340.0k | 3.1 |
| m7i.4xlarge | 16 | 64 GiB | 1.30M | 690.0k | 6.1 |

{/* end:starting-table */}

AWS vCPU counts are logical CPU threads. These instance types use two threads
per physical core.

Each server uses a 200 GiB gp3 volume provisioned for 6,000 IOPS and 500 MiB/s.
The EC2 instance's EBS throughput limits also apply. The load generator runs on
a separate on-demand host after Spot interruptions disrupted early generator
runs. Arc runs through systemd from the released native package.

The package's ingestion buffer settings are 5,000,000 points and a 100 ms
maximum buffer age. Parquet ingestion and normal background compaction remain
enabled. These settings affect flush size, file count, memory, and query cost;
changing them creates a different sizing workload.

The 4-, 8-, and 16-vCPU instance EBS baseline bandwidths are approximately
156, 313, and 625 MB/s respectively. The smaller instances can burst above
their baselines. A short test can therefore exceed the bandwidth available for
continuous operation. Size storage for the sustained volume and instance
limits, including simultaneous WAL and Parquet writes.

## What a write means

A point is one row with a timestamp, a host tag, and three numeric fields:
`value`, `cpu_idle`, and `cpu_user`. Columnar MessagePack and line protocol write
the same `cpu` measurement with the same schema and values, using 5,000-point
batches without HTTP payload compression. Field values are independently
generated in the range 0–100 and rounded to four decimal places. Persisted
Parquet uses the release's default Zstd compression.

The tables report **points per second**. For this dataset, multiply that rate by
three to obtain numeric field values per second. State the number of fields when
comparing these results with a benchmark expressed in field writes.

The main workload has 10,000 distinct hosts in one measurement. The sensitivity
test has 100,000 hosts. Here, a host series means a measurement and host pair;
including each field separately gives 30,000 and 300,000 field series.

Sustained ingestion replays 256 pre-generated batches to keep client data
generation out of the throughput measurement. Arc appends these rows, including
repeated timestamps and values. Treat the results as batched synthetic workload
measurements and validate a representative production stream before committing
to a capacity target.

## WAL enabled and disabled

These are achieved rates from fully reconciled ten-minute ingestion runs, with
zero HTTP errors, WAL drops or write failures, and flush failures. The same
selected MessagePack offered rate on several sizes is a result of the coarse
rate-selection steps; it does not demonstrate an identical hardware ceiling.

{/* begin:wal-table */}

| Instance | WAL | MessagePack points/sec | Line protocol points/sec |
| --- | --- | --- | --- |
| m7i.xlarge | Enabled | 2.79M | 349.7k |
| m7i.xlarge | Disabled | 3.99M | 699.2k |
| m7i.2xlarge | Enabled | 2.80M | 699.1k |
| m7i.2xlarge | Disabled | 5.59M | 1.40M |
| m7i.4xlarge | Enabled | 2.80M | 1.40M |
| m7i.4xlarge | Disabled | 5.59M | 1.40M |

{/* end:wal-table */}

WAL-disabled capacity applies to workloads that can tolerate losing buffered
writes after an abrupt failure. Use the WAL-enabled figures when sizing a
deployment that relies on the ingestion WAL. The enabled case uses the released
WAL implementation, including its batching; this campaign does not measure a
per-request disk-sync barrier.

For a WAL-disabled ingestion-only starting target, apply the same 50% headroom
rule to its measured rate. A comparison of different offered rates shows the
validated operating points; it does not isolate the overhead of WAL itself.
The report also includes WAL-on/off MessagePack runs at the same offered rate
to examine resource overhead separately.

For configuration and recovery behavior, see [Write-Ahead Log](/arc/advanced/wal/).

## Query workloads

Query-only tests start with exactly 20 million unique points spread over 24
hours. They use an equal mix of three SQL queries:

| Query | Time range | Work performed |
| --- | --- | --- |
| Minute aggregates | 1 hour | Average two fields and find the maximum of a third, grouped by minute |
| Fleet aggregates | 24 hours | Group by host, compute averages, maxima, and counts, and return the top 100 hosts |
| Host aggregates | 24 hours | Compute counts, averages, minima, and maxima for one host |

All query cases use the SQL endpoint with JSON requests and responses.
Reported latency includes the HTTP request and reading the complete response.
Arc's SQL and file metadata caches, and the operating-system caches, use their
normal warm behavior. Every request executes a query against stored data.

QPS applies to this query mix and retained data volume. A dashboard with bounded
time windows and small result sets has different resource requirements from
large scans, exports, joins, or aggregations over a longer retention period.

Each query-only candidate runs for 30 seconds after a five-second warmup, with
three repeats. The table selects the highest median QPS among candidates for
which all three repeats have no errors and each query type's p95 is at most
two seconds. It reports the worst p95 across those repeats, rather than merging
the latency distributions.

The WAL cases are seeded separately and can have different Parquet file layouts.
Small differences in read-only QPS are not an isolated measurement of WAL
overhead; no ingestion is running in this table.

## Ingestion and queries together

Each combined run restores the same 20-million-point starting snapshot for its
WAL and cardinality case. It then ingests additional points while the query mix
runs. The report records the ending data volume, achieved write rate, achieved
QPS, and latency by minute.

The offered write rate is the same for both protocols: 100,000 points/sec,
capped at half the slower protocol's validated sustained rate. Offered query
load is 25% of that hardware and cardinality case's query-only QPS. This tests
a defined evaluation scenario; it does not establish maximum combined capacity.

A separate MessagePack evaluation run starts at 10% of query-only QPS while
keeping the same write target and data growth, for both WAL settings. If the
requested query rate is not achieved, the campaign halves it and repeats the
ten-minute run. The starting guidance uses achieved rates and reports the
observed query latency with them.

Both combined tables report the **worst p95 among the three query types over
the full run**. Meeting an offered QPS target does not establish a latency
service level. Compare these latencies with your application's requirement;
the retained volume grows throughout the run, so later minutes can be slower.

## Resource observations

The following MessagePack comparison uses the **same 2.8M offered points/sec**
for WAL enabled and disabled, each for ten minutes. It reports sampled native
process RSS and host CPU/I/O behavior, including DuckDB and Arrow allocations.
CPU busy excludes I/O wait. RSS is sampled approximately every five seconds,
so brief peaks can occur between samples. The raw report also preserves disk
intervals; those short samples do not establish sustained storage bandwidth.
Paired runs use the same instance type but can run on replacement hosts; their
purchase history and burst-credit state are not a controlled variable.

{/* begin:resource-table */}

| Instance | WAL | Achieved points/sec | Median CPU busy | Median I/O wait | Peak sampled Arc RSS |
| --- | --- | --- | --- | --- | --- |
| m7i.xlarge | on | 2.79M | 47% | 14.9% | 2.01 GiB |
| m7i.xlarge | off | 2.80M | 43% | 0.4% | 0.41 GiB |
| m7i.2xlarge | on | 2.80M | 24% | 8.8% | 0.85 GiB |
| m7i.2xlarge | off | 2.80M | 22% | 0.7% | 0.26 GiB |
| m7i.4xlarge | on | 2.80M | 11% | 4.6% | 0.94 GiB |
| m7i.4xlarge | off | 2.80M | 11% | 0.3% | 1.57 GiB |

The 16-vCPU line-protocol runs also use the same 1.40M offered points/sec. Median CPU busy is 43% with WAL enabled and 26% with WAL disabled; median I/O wait is 4.8% and 0.2% respectively. Both achieve the write target and reconcile every acknowledged point.

{/* end:resource-table */}

In the higher-query-demand combined runs, the 4- and 8-vCPU servers approach
full CPU utilization while retaining substantial available RAM and low disk
wait. For this growing dataset, lowering query demand addresses the measured
constraint. That observation does not establish RAM requirements for a larger
retained dataset, different queries, or sustained compaction.
Scheduled compaction can overlap individual runs, and separately seeded cases
can have different file layouts. Do not attribute every small difference in
latency or achieved QPS solely to the ingestion format or WAL setting.

## Storage and retention

Estimate retained data from the **unique historical seed's** measured storage
size. Sustained ingestion replays pre-generated batches to reduce generator
overhead, so its compression ratio is unsuitable for estimating production
retention storage.

The seed estimate measures the initial persisted local data directory before manual
compaction. Use it as a sample-based storage estimate, rather than a guarantee
of compression after every retention or compaction policy.

{/* begin:storage-table */}

| Hosts | Unique points | Persisted bytes/point | Total local data size |
| --- | --- | --- | --- |
| 10,000 | 20M | ~26.2 | ~499 MiB |
| 100,000 | 20M | ~27.6 | ~526 MiB |

{/* end:storage-table */}

```text
points per day = points per second × 86,400
retained data bytes = points per day × retention days × measured bytes per point
```

Add space for the WAL, compaction output and spill, operational metadata, and
free disk headroom. Compression depends on field count and types, string
cardinality, values, ordering, and compaction. Measure bytes per point using a
sample that represents your own data.

Using a rounded **28 bytes per point** for this schema, 10,000 points/sec with
30 days of retention needs about **676 GiB** for stored data alone. At 100,000
points/sec that becomes about **6.6 TiB**. The 200 GiB test volume is a benchmark
configuration, not a recommendation for those retention workloads.

## When to use a larger server

Increase CPU capacity when the query mix consumes the headroom needed by
ingestion, or when query latency exceeds your application's target. The number
of rows and columns scanned, aggregation groups, and concurrent queries matter
as much as the number of requests.

Increase RAM when native process memory grows toward the machine's available
memory, or queries and compaction need larger working sets. Track native Arc RSS
and operating-system memory availability alongside Go heap metrics: DuckDB and
Arrow allocations are part of the process's memory requirement.

Increase storage throughput when flushes fall behind, buffer queues grow,
reconciliation takes longer, or disk wait rises. Provision against the lower of
the volume and instance limits, and leave headroom for compaction. A faster CPU
does not resolve a storage throughput limit.

## Reproducing the measurements

Use the [native sizing harness](https://github.com/Basekick-Labs/arc-benchmarks/tree/d8aaf8ccd69008467505e3745004a95106558b1a/sizing_bench)
and the [October 12 results and raw evidence](https://github.com/Basekick-Labs/arc-benchmarks/tree/d8aaf8ccd69008467505e3745004a95106558b1a/sizing_bench/results/oss-26.09.3-20261012).
These links pin the source and measurements to the recorded campaign commit.
The archive includes rejected overload and interrupted cases separately from
qualified results, with checksums and instructions to regenerate the analysis.

The campaign increases offered ingestion rates, validates the boundary, repeats
acceptable rates, and runs ten-minute ingestion tests with headroom. A usable
WAL-enabled run has zero WAL drops and write failures. Every ingestion test
reconciles acknowledged points with a SQL row count after flushing completes.
Rate selection uses coarse steps and a halving fallback when confirmation
fails; selected rates are validated operating points, not precise maxima.
Each historical seed triggers compaction and waits ten seconds before the
snapshot. Normal scheduled compaction remains enabled. These short tests do
not qualify steady-state retention, compaction, or restart recovery.

The raw report preserves the native package checksum, configuration, schema,
query SQL, worker and batch settings, latencies, memory, CPU, disk metrics, and
invalid overload cases. Derived starting targets are presented separately
from measured operating points.
