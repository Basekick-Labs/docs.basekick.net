Publish Arc's data as **Apache Iceberg** tables so any Iceberg-aware engine — Spark, Trino, DuckDB, Snowflake, PyIceberg — can query it directly, without going through Arc.

<Callout type="info" title="Availability">
Iceberg export is available in **Arc 26.09.1+**. Enable it with `iceberg.enabled = true`.
</Callout>

## What it is

[Apache Iceberg](https://iceberg.apache.org/) is an open **table format**: a metadata layer that turns a collection of data files into a coherent, transactional table with schema, snapshots, and partition information. It is **not a file format** — Iceberg tables are backed by Parquet (which Arc already writes).

Arc's Iceberg export is a background **reconciler** that registers Arc's **existing** Parquet files into an Iceberg table *by reference*, and keeps the table's file list in sync as compaction and retention change the underlying files.

## Why use it

- **No lock-in, taken further.** Arc already stores open Parquet files you own. Iceberg export makes those same files a standard lakehouse table that the entire Iceberg ecosystem can read — no proprietary API in the path.
- **Zero-copy.** Files are registered in place using Iceberg's `add_files` semantics. **No data is copied or rewritten**, so there is effectively no storage overhead beyond small Iceberg metadata. (This is a real differentiator: many streaming/TSDB systems re-export data into *new* Parquet; Arc doesn't need to, because it already writes Parquet.)
- **Query with your existing tools.** Spark, Trino, DuckDB, Snowflake, Dremio, and PyIceberg all read Iceberg. Point them at Arc's data instead of building a custom connector.
- **Ingest is untouched.** The export runs on a background timer and never touches Arc's high-throughput write path.

## How it works

1. Arc ingests as usual, writing Parquet under `{database}/{measurement}/{Y}/{M}/{D}/{H}/`.
2. On a timer (default every 5 minutes), the reconciler walks each measurement's Parquet files and diffs them, by path and size, against the Iceberg table's current file set.
3. It commits the delta in one Iceberg snapshot — adding newly-written files and removing files that compaction/retention deleted — **without rewriting any data**. Since 27.01.1 the row-level delete API publishes a rewritten file under a fresh path rather than replacing the original in place, so a partial delete reaches the table as a normal add-and-remove.
4. Old snapshots are expired on a retention policy so metadata stays bounded. A pass that removes any file expires **all** older snapshots, because they reference files Arc has deleted — see [Time travel](#time-travel) below.

Because the reconciler is driven by what's actually on storage (not a transient event stream), it is **self-healing**: a missed or failed pass simply converges on the next tick. Measurements whose file set hasn't changed since the last pass are skipped entirely, so steady state is cheap.

This holds all the way to zero: if retention ages out *every* file in a measurement, the table is reconciled to empty rather than left pointing at files that no longer exist — so external engines see an empty table instead of failing on missing paths.

Tables are created per database/measurement in the namespace `<namespace_prefix>_<database>` (default prefix `arc`), e.g. `arc_mydb.sensors`.

## Quick start

```toml
# arc.toml
[storage]
backend = "local"          # "local" or "s3" (see Limitations)

[iceberg]
enabled = true             # default: false
```

Or via environment variable:

```ini
ARC_ICEBERG_ENABLED=true
```

Restart Arc. Within one reconcile interval, ingested measurements appear as Iceberg tables under your storage root (`{local_path}/arc_<database>.db/<measurement>/`).

### On S3

Iceberg export also runs on an S3 primary, on AWS or an S3-compatible store:

```toml
[storage]
backend = "s3"
s3_bucket = "my-arc-bucket"
s3_prefix = "prod/"        # optional
s3_region = "us-east-1"

[iceberg]
enabled = true
```

Tables land under the storage root, at `s3://my-arc-bucket/prod/arc_<database>.db/<measurement>/`.

- **Credentials:** the export uses Arc's own S3 credentials and renews them the same way Arc does: static keys, the default chain, IRSA on EKS, or an assumed role. No credential is written into Iceberg metadata, the catalog or the logs.
- **Endpoint:** `storage.s3_endpoint` and `storage.s3_path_style` apply to the export too. The `AWS_S3_ENDPOINT` environment variable does not change where it writes.
- **Readers:** readers need their own read access to the bucket.
- **Enabling on an existing deployment:** the first pass registers every existing data file. It reads each file's footer twice (two ranged GETs, never the whole object). After a restart, an unchanged table reads no footers.

## Reading the tables

### DuckDB

The simplest way to read a table — point `iceberg_scan` at the table directory:

```sql
INSTALL iceberg; LOAD iceberg;

SELECT count(*)
FROM iceberg_scan('/var/lib/arc/data/arc_mydb.db/cpu');
```

Arc emits a `version-hint.text` in each table's `metadata/` directory, so directory-based readers like DuckDB resolve the current snapshot without needing the exact metadata filename.

On S3, give DuckDB an S3 secret and point it at the table's `s3://` directory:

```sql
INSTALL iceberg; LOAD iceberg; INSTALL httpfs; LOAD httpfs;

CREATE SECRET (TYPE s3, PROVIDER credential_chain, REGION 'us-east-1');
-- S3-compatible store: TYPE s3, KEY_ID '…', SECRET '…', ENDPOINT 'minio:9000', URL_STYLE 'path', USE_SSL false

SELECT count(*)
FROM iceberg_scan('s3://my-arc-bucket/prod/arc_mydb.db/cpu');
```

### PyIceberg

PyIceberg can read through Arc's SQLite catalog directly:

```python
from pyiceberg.catalog.sql import SqlCatalog

cat = SqlCatalog("arc", **{
    "uri": "sqlite:////var/lib/arc/data/arc.db",     # Arc's catalog DB
    "warehouse": "file:///var/lib/arc/data",          # storage root
})

table = cat.load_table(("arc_mydb", "cpu"))
df = table.scan().to_arrow()
print(df.num_rows, df.column_names)
```

On S3, pass PyIceberg the `s3.*` properties. Arc's SQLite catalog is on the node that runs the reconciler, so from any other host load the table from its directory instead; PyIceberg resolves the current version from `version-hint.text`:

```python
from pyiceberg.table import StaticTable

s3 = {
    "s3.region": "us-east-1",
    # S3-compatible store:
    # "s3.endpoint": "http://minio:9000",
    # "s3.access-key-id": "…", "s3.secret-access-key": "…",
}

table = StaticTable.from_metadata("s3://my-arc-bucket/prod/arc_mydb.db/cpu", properties=s3)
print(table.scan().to_arrow().num_rows)
```

On the reconciler node, the catalog works with the same properties: `SqlCatalog("arc", uri="sqlite:////var/lib/arc/data/arc.db", warehouse="s3://my-arc-bucket/prod", **s3)`.

### Apache Spark

Read a table from its directory with the Iceberg runtime and a Hadoop-style catalog, or load it directly:

```python
df = (spark.read.format("iceberg")
      .load("file:///var/lib/arc/data/arc_mydb.db/cpu"))
df.printSchema()
df.createOrReplaceTempView("cpu")
spark.sql("SELECT count(*) FROM cpu").show()
```

On S3, add `hadoop-aws` and map the `s3://` scheme Arc writes to the S3A filesystem:

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
    .config("spark.jars.packages",
            "org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.7.1,"
            "org.apache.hadoop:hadoop-aws:3.3.4")
    .config("spark.hadoop.fs.s3.impl", "org.apache.hadoop.fs.s3a.S3AFileSystem")
    # S3-compatible store: fs.s3a.endpoint, fs.s3a.path.style.access, fs.s3a.access.key / secret.key
    .getOrCreate())

df = spark.read.format("iceberg").load("s3://my-arc-bucket/prod/arc_mydb.db/cpu")
```

### Trino / Snowflake / others

Any engine with an Iceberg connector can read the tables. For engines that require a shared catalog service (Trino's JDBC catalog supports PostgreSQL/MySQL, not SQLite), point the connector at the Iceberg metadata; a shared REST or JDBC catalog in front of the warehouse is the path for broad multi-engine access. See **Limitations** below.

## Configuration reference

| Key (`arc.toml`) | Env var | Default | Meaning |
|---|---|---|---|
| `iceberg.enabled` | `ARC_ICEBERG_ENABLED` | `false` | Enable the export reconciler. |
| `iceberg.reconcile_interval` | `ARC_ICEBERG_RECONCILE_INTERVAL` | `300` | Seconds between reconcile passes. |
| `iceberg.retain_snapshots` | `ARC_ICEBERG_RETAIN_SNAPSHOTS` | `10` | Iceberg snapshots (and metadata versions) kept per table; older are expired to bound metadata growth. An upper bound, not a guarantee: a pass that removes a file expires all older snapshots regardless of this value, because they reference deleted files (see [Time travel](#time-travel)). |
| `iceberg.namespace_prefix` | `ARC_ICEBERG_NAMESPACE_PREFIX` | `arc` | Namespace prefix; tables land in `<prefix>_<database>`. |
| `iceberg.warehouse` | `ARC_ICEBERG_WAREHOUSE` | *storage root* | Root URI where table metadata is written (`file://` or a plain path; `s3://` with an S3 backend). Defaults alongside the data. On local storage, a warehouse outside the storage root works but Arc cannot publish `version-hint.text` for directory-based readers, and backups copy the warehouse separately. With an S3 backend it must be inside the storage root (`s3://<s3_bucket>/<s3_prefix>/…`); Arc refuses to start otherwise. Since 27.01.1 the warehouse's directories inside the storage root are not databases; see [The warehouse is not a database](#the-warehouse-is-not-a-database). |
| `iceberg.layout` | `ARC_ICEBERG_LAYOUT` | `warehouse` | Where new tables are created (27.01.1+): `warehouse` puts metadata under `<warehouse>/<prefix>_<database>.db/<measurement>`; `colocated` puts it in `<database>/<measurement>/metadata/`, beside the data. See [Table layout](#table-layout). |
| `iceberg.catalog_db_path` | `ARC_ICEBERG_CATALOG_DB_PATH` | *shared auth DB* | SQLite catalog location. |
| `iceberg.cold_rescan_interval` | `ARC_ICEBERG_COLD_RESCAN_INTERVAL` | `3600` | With an S3 cold tier: seconds a measurement's cached cold-tier listing is trusted. Arc re-lists right away after its own cold-tier changes (migrations, cold retention, DELETE, database delete); this only bounds changes made outside Arc. |
| `iceberg.orphan_sweep_enabled` | `ARC_ICEBERG_ORPHAN_SWEEP_ENABLED` | `true` | Delete manifest files that no retained metadata version references any more. This is the one thing the exporter deletes that nothing regenerates, so it has an off switch; set `false` and the manifests of expired snapshots are kept forever and copied into every backup. Arc logs a warning at startup when it is off. |

## Table layout

Since Arc 27.01.1, `iceberg.layout` decides where a new table's metadata goes.

- **`warehouse` (the default).** Metadata in `<warehouse>/<prefix>_<database>.db/<measurement>/metadata/`, apart from the data. Manifests point at Arc's Parquet files by absolute path.
- **`colocated`.** The table's location is the measurement's own directory, so its metadata goes in `<database>/<measurement>/metadata/` and every data file it references is inside the table folder.

Use `colocated` for readers that reach a table only through its folder and cannot follow paths outside it. A Microsoft Fabric OneLake shortcut is one: with the default layout it converts the metadata, then fails on the first data file. See [Microsoft Fabric and Power BI](/arc/integrations/microsoft-fabric/#zero-copy-iceberg-through-onelake).

```toml
[iceberg]
enabled = true
layout  = "colocated"
```

- `colocated` needs local or S3 storage and the warehouse at the storage root (the default). Arc refuses to start with `iceberg.warehouse` pointing elsewhere.
- **The layout applies to new tables only.** An existing table keeps its location, so switching the key, either way, moves nothing. To move a table: stop Arc on **every** node, delete the table's row from the `iceberg_tables` table of each node's catalog, delete its metadata directory (`<prefix>_<database>.db/<measurement>/` when moving to colocated, `<database>/<measurement>/metadata/` when moving back), and start Arc. The next pass recreates the table and registers every file again, reading each file's footer once.
- **Same layout on every node** that exports to the same storage, or two nodes could each create the table in a different place.
- A measurement's `metadata/` directory is not data: queries, pruning and the schema registry ignore it, and a database `DELETE` removes it through the Iceberg cleanup.

<Callout type="warn" title="Never run orphan-file cleanup on a colocated table">
A colocated table's location holds Arc's data, including files the export has not registered yet. `remove_orphan_files` (Spark, Trino) deletes every file under the location that no snapshot references, which would delete Arc data.
</Callout>

Caveats:

- **Cold tier.** Files that tiering moves to a cold tier leave the table folder. The table still lists them, so catalog readers see them, but folder-scoped readers such as a OneLake shortcut cannot read them. Arc warns at startup.
- **Cluster with node-local storage.** The metadata exists only on the exporting node. Arc warns at startup.
- **Object storage.** A measurement whose data is all gone but whose table metadata remains is still listed.

## The warehouse is not a database

Since Arc 27.01.1, with Iceberg export on, Arc no longer treats the
warehouse's directories inside the storage root as databases, on local
storage and on S3 alike. Earlier versions listed them with the databases,
accepted writes into a subdirectory warehouse, and let a database `DELETE`
remove the warehouse's metadata. What is hidden depends on where
`iceberg.warehouse` points:

- **The storage root (the default).** The namespace directories
  (`<prefix>_<database>.db`, for example `arc_telemetry.db`) sit next to the
  databases.
- **A subdirectory of the storage root**, for example `<root>/lv_wh`. The
  directory `lv_wh` sits next to the databases and holds the namespace
  directories.
- **Deeper inside the storage root**, for example `<root>/a/b`. Database `a`
  may be a real one and stays listed; only its measurement `b` is the
  warehouse.

For a namespace directory and for a subdirectory warehouse:

- `GET /api/v1/databases`, `SHOW DATABASES` and `GET /api/v1/measurements`
  leave them out, and `SHOW TABLES` lists no tables in them.
- `GET /api/v1/databases/{name}` and its `/measurements` answer `404`.
- `DELETE /api/v1/databases/{name}` answers `403`.
- A tiering policy `PUT` for them answers `404`.

A subdirectory warehouse's name is also refused as a database name:

- `POST /api/v1/databases` answers `400 Database name 'lv_wh' is reserved`.
- A write to a database of that name answers
  `400 database name "lv_wh" is reserved for the Iceberg warehouse`: line
  protocol, MessagePack, TLE and every `/api/v1/import/*` format. Creating or
  updating a continuous query with that database answers the same `400`, and
  a stored one fails its runs. An MQTT subscription or `topic_mapping` rule
  that targets it is refused, and a message that maps to it is dropped and
  counted as failed.
- The match is exact: `lv_wh-other` is an ordinary database. On a volume that
  does not distinguish case, another spelling such as `LV_WH` is refused only
  once the warehouse directory exists.

For a warehouse nested deeper, at `<root>/a/b`:

- Measurement `b` of database `a` is left out of the listings.
- `DELETE` of database `a` answers `403`, because it would delete the
  warehouse with it. Move the warehouse first.
- Writes to measurement `b` of database `a` are **not** refused. They land
  inside the warehouse directory, are hidden from the listings and are not
  exported. Do not write there; a warning at startup names that measurement.

The export applies the same rule, so it does not export a subdirectory
warehouse as if it were a database.

<Callout type="warn" title="Configure Iceberg the same way on every node">
In a cluster, the rule holds only on nodes with Iceberg export on. A node with
`iceberg.enabled = false` lists the warehouse as a database and accepts writes
to it.
</Callout>

## Schema mapping

Arc's columns map to Iceberg types as follows:

| Arc / Arrow | Iceberg |
|---|---|
| `time` (Timestamp µs, UTC) | `timestamptz` |
| int64 | `long` |
| int32 | `int` |
| float64 | `double` |
| float32 | `float` |
| string | `string` |
| bool | `boolean` |
| binary | `binary` |
| decimal128 | `decimal(P,S)` |

Arc's own ingest writes int64, float64, string, bool, binary (MessagePack `bin` values, since v27.01.1) and timestamps; the 32-bit and decimal types are there for Parquet that arrives through the bulk import API.

Tables are partitioned by `day(time)`.

### Schema changes

**Adding columns is automatic.** If a measurement gains a column over time, the Iceberg table's schema is evolved to include it, and older files (written before the column existed) stay readable — the new column simply reads as `NULL` for those rows.

**Changing a column's type is not supported.** If a column's type changes (say `value` was written as an integer and later arrives as a float), Iceberg cannot represent both in one column. Arc refuses to reconcile that measurement and logs an error naming the column and both types:

```bash
column "value" type mismatch: Iceberg table has long, new Parquet files have double
(the measurement's column type changed; Iceberg cannot represent both in one column)
```

The Iceberg table is left untouched and stays readable at its last good state, and your other measurements keep exporting normally — one bad measurement never blocks the rest. Arc retries on every reconcile pass, so once the underlying type conflict is resolved the measurement recovers on its own without a restart.

The conflict lives in the data, not in Iceberg, so fix it at the source: keep a measurement's column type stable, or write the new type under a different column or measurement name.

## Time travel

**Arc does not support Iceberg time travel across compaction, retention or a partial DELETE.** Reading the current snapshot is fully supported; reading an older one is only sound while nothing has removed a file since.

The reason is a genuine conflict rather than an omission. Iceberg copy-on-write keeps a superseded data file alive until the snapshots that reference it expire. Arc cannot: it reads a partition with a glob over every Parquet file in it, so a superseded file left in place would be counted twice by every ordinary query. Arc therefore deletes the file, and the snapshots naming it stop being readable.

So that a reader gets a meaningful error rather than one that looks like data loss, a reconcile pass that removes any file now expires every older snapshot. Time travel to one returns:

```
Invalid Configuration Error: Could not find snapshot with id 873009943563408273
```

which is the ordinary result of any Iceberg retention policy, instead of:

```
IO Error: Cannot open file ".../cpu_20261008_155058_567682000.parquet": No such file or directory
```

which is indistinguishable from the object store having lost an object. No readable history is lost by this: a removed file is referenced by every snapshot from the one that added it onward, so each of those had already stopped working.

What this means in practice: compaction runs hourly by default, so on an actively-ingesting measurement expect history to be one snapshot deep most of the time. A measurement that only ever gains files keeps `retain_snapshots` of genuinely readable history, because nothing has been removed.

Two edges worth knowing:

- The expiry applies to `version-hint.text`, which is how directory-based readers resolve the table. Arc also keeps `retain_snapshots + 1` older `v<N>.metadata.json` copies for readers that pin a version, and those still list the pre-expiry snapshots — a consumer reading one directly still gets the `IO Error` until the copy is pruned, roughly `retain_snapshots` passes later.
- On a deployment upgrading into this behaviour, a table's stale history is cleaned by its next pass that removes something. A table whose file set has gone quiet is skipped by the reconciler, so it keeps the old snapshot list until it changes again.

A pass that expires history this way logs at `warn` with the snapshot counts before and after.

If you need reproducible reads of historical state, snapshot the query results rather than the table, or use Arc's backup and restore.

## Cold-tier tiering

With an S3 cold tier (`tiered_storage.cold.backend = "s3"`), a file that tiering moves to cold stays in the Iceberg table under its `s3://` URI, with the same rows and statistics. Readers see the same data before, during and after a migration.

- **Mixed-location tables:** with a local primary, a table holds `file://` paths for hot data and `s3://` paths for cold data. A reader needs access to both: run it on the Arc host, with S3 credentials for the cold bucket. For a table every host can read, use an S3 primary too (`storage.backend = "s3"`).
- **Glacier:** Arc writes cold objects to S3 Standard. If a bucket lifecycle rule moves them to Glacier or Deep Archive, the table still lists them, and external engines cannot read them until they are restored. Arc's export does not restore objects or skip archived ones.
- **Which copy is exported:** the one Arc's queries read. While a file is on both tiers, during a migration or for a hot-only database, the table keeps the hot copy until Arc's tier record says the file is cold.
- **No extra reads:** a migrated file's entry is copied from the hot one. The cold object is read only for cold data the table never held hot, and then with the cold tier's own credentials.
- **Brief read error, never wrong rows:** in the one reconcile pass between a migration deleting the hot copy and the table moving to the cold URI, a reader that already resolved the old path can get a not-found error. Compaction and retention have the same window.
- **Licensing:** tiering requires an Enterprise license. Without it Arc disables tiering, and with a cold tier still configured the export does not start; tables keep their last snapshot until the license is restored. The same applies if the configured cold tier is unavailable at startup.

## Limitations (v1)

- **Local or S3 storage.** Iceberg export runs with `storage.backend = "local"` or `"s3"`. Arc **refuses to start** with Iceberg enabled on:
  - an Azure or GCS primary;
  - an S3 backend pointed at Google Cloud Storage's S3-compatible endpoint (`storage.googleapis.com`);
  - an S3 backend whose `iceberg.warehouse` is outside the storage root.
- **Cold tier on S3 only.** Iceberg export runs alongside cold-tier tiering when the cold tier is S3 (see [Cold-tier tiering](#cold-tier-tiering)). Arc refuses to start with Iceberg enabled and an Azure or GCS cold tier, or an S3 cold tier on Google Cloud Storage's interop endpoint, because files migrated there would leave the table.
- **Eventual consistency.** The Iceberg view reflects the last reconcile pass, so it lags live ingest by up to `reconcile_interval`. This is expected for a lakehouse export.
- **On-disk portability.** Iceberg metadata references files by absolute path. Tables read fine on the same host; moving a local table to a different path/host requires re-pointing (object-store warehouses avoid this).
- **Catalog discovery.** Catalog-aware access works today via the SQLite catalog (PyIceberg) or by pointing engines at the table directory (DuckDB, Spark). Broad multi-engine *catalog* discovery (Trino, Glue) would use a REST/JDBC catalog in front of the warehouse — a deployment choice beyond v1.
- **Metadata is bounded, not constant.** Each reconcile pass that removes a file writes new manifests and leaves the superseded ones behind, so the metadata directory grows with the removal history rather than with the data. Two mechanisms bound it, both automatic: the orphan sweep (above) deletes manifests no retained metadata version references, and a pass that finds a table at 12 or more data manifests merges them into one. Expect on the order of `retain_snapshots` commits' worth of `.avro` in a steady state. A table whose file set has stopped changing is skipped by the reconciler, so it keeps whatever manifest count it last had until something writes to it again.
- **Clustered deployments.** Exactly one node must run the reconciler.
  - Under the compactor failover lease this is guaranteed.
  - In a static-role cluster with local storage, enable Iceberg export where a single compaction-capable node runs.
  - **With shared storage** (`cluster.shared_storage_mode`), Iceberg export requires `cluster.failover_enabled = true`, and only the node holding the compactor lease exports. No node exports before the first lease is assigned.
  - The version published in the bucket, not a node's own catalog, is the table's current version. A node that takes over, or comes back after a failover, continues from it.
  - If two nodes ever commit the same version, the second is refused, logged as `another writer published this table version first`, and it adopts the published version on its next pass.
  - A node whose SQLite catalog was lost also continues the existing table rather than starting a second one in the same directory.
  - The SQLite catalog is local to the node that exports, so catalog-based readers (PyIceberg's `SqlCatalog`) work only there. From any other host, read the table from its `s3://` directory (DuckDB, PyIceberg `StaticTable`, Spark).

## Backup & restore

Arc's backup includes the Iceberg warehouse metadata (`metadata.json`, manifest `.avro`, `version-hint.text`) alongside the Parquet data, so a restored deployment keeps its Iceberg tables intact. On S3 the warehouse is always inside the storage root, so the metadata travels with the data. A warehouse outside the storage root is backed up too, under `iceberg/` in the backup, and restored into the node's configured `iceberg.warehouse`. Both the storage root and the warehouse are recorded by absolute path in the Iceberg metadata, so restore to the same paths; see [Backup & restore](/arc/operations/backup-restore/) for the details and the cluster caveat.

## FAQ

**Does this slow down ingestion?** No. The export is a background reconciler; the write path is unchanged.

**Does it duplicate my data?** No. It registers your existing Parquet files by reference. Only small Iceberg metadata is written.

**Can I still use Arc's SQL API?** Yes. Iceberg export is additive — Arc's native query API is unaffected. The same Parquet files serve both.

**What happens to compacted/retained files?** The reconciler reflects them. Retention deletes show up as file removals on the next pass. A compacted file is registered only once its compaction has committed, that is, once its source files are gone; until then the source files stay in the table, so a pass that runs in the middle of a compaction never registers both the sources and their replacement. If a compaction deletes some of its sources and fails on the rest, the compacted file stays out of the table and the surviving sources stay in it until the next compaction cycle's recovery finishes the job: a bounded under-count, never a double count.

**What about the row-level delete API?** A delete that matches every row in a file removes the file, and the next pass drops it from the table. A delete that matches only some rows rewrites the file in place at the same path; the reconciler notices the changed file size and re-registers the file in a single commit, so the table's record count and file size follow the rewrite within one reconcile interval instead of keeping the values from the original registration. That commit merges the table's manifests into one (Iceberg's `commit.manifest-merge.enabled`, enabled for that commit only), which is what lets a path that already left the table come back.
