Arc accepts MessagePack for efficient typed batches and InfluxDB line protocol for simple, portable writes. Both APIs return `204 No Content` when a write is accepted.

| Use case | Recommended path |
| --- | --- |
| Application writes and large batches | MessagePack columnar |
| Shell scripts and existing InfluxDB clients | Line protocol |
| Host, service, and infrastructure metrics | [Telegraf](/arc/integrations/telegraf/) |
| Historical files | [Data import](/arc/data-import/) |

The examples use a database named `metrics` and read the token from `ARC_TOKEN`. Export the token together with `ARC_ENDPOINT`, then create the database once before writing:

```bash
export ARC_TOKEN="<api-token>" ARC_ENDPOINT=http://localhost:8000
arcli db create metrics
```

arcli reads `ARC_TOKEN` from the environment only together with `ARC_ENDPOINT`. With the token exported on its own, arcli commands that use the environment fail with `ARC_TOKEN needs ARC_ENDPOINT`.

## MessagePack

Send MessagePack to `POST /api/v1/write/msgpack`. The columnar format groups values by column, which keeps batches compact:

```json
{
  "m": "cpu",
  "columns": {
    "time": [1788973200000000, 1788973201000000],
    "host": ["server01", "server02"],
    "usage": [45.2, 67.8]
  }
}
```

- `m` is the measurement name.
- Every array in `columns` must have the same length.
- Values within a column must use a consistent type.
- `time` is a numeric Unix timestamp. Arc detects seconds, milliseconds, microseconds, or nanoseconds by magnitude.

<Tabs items={['curl', 'Python', 'Go']}>
  <Tab value="curl">

`curl` can send an already encoded MessagePack file:

```bash
curl --request POST http://localhost:8000/api/v1/write/msgpack \
  --header "Authorization: Bearer $ARC_TOKEN" \
  --header "Content-Type: application/msgpack" \
  --header "x-arc-database: metrics" \
  --data-binary @cpu.msgpack
```

Use the Python or Go example to encode a payload, then write the resulting bytes to `cpu.msgpack` when a file-based workflow is useful.

  </Tab>
  <Tab value="Python">

Install the dependencies:

```bash
python -m pip install msgpack requests
```

Then encode and send a batch:

```python
import os
import time

import msgpack
import requests

now = time.time_ns() // 1_000
payload = {
    "m": "cpu",
    "columns": {
        "time": [now, now + 1_000_000],
        "host": ["server01", "server02"],
        "usage": [45.2, 67.8],
    },
}

response = requests.post(
    "http://localhost:8000/api/v1/write/msgpack",
    headers={
        "Authorization": f"Bearer {os.environ['ARC_TOKEN']}",
        "Content-Type": "application/msgpack",
        "x-arc-database": "metrics",
    },
    data=msgpack.packb(payload, use_bin_type=True),
    timeout=10,
)
response.raise_for_status()
```

  <Tab value="Go">

Add a MessagePack encoder:

```bash
go get github.com/Basekick-Labs/msgpack/v6
```

Then encode and send a batch:

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"log"
	"net/http"
	"os"
	"time"

	"github.com/Basekick-Labs/msgpack/v6"
)

type payload struct {
	Measurement string         `msgpack:"m"`
	Columns     map[string]any `msgpack:"columns"`
}

func main() {
	now := time.Now().UnixMicro()
	data, err := msgpack.Marshal(payload{
		Measurement: "cpu",
		Columns: map[string]any{
			"time":  []int64{now, now + 1_000_000},
			"host":  []string{"server01", "server02"},
			"usage": []float64{45.2, 67.8},
		},
	})
	if err != nil {
		log.Fatal(err)
	}

	req, err := http.NewRequest(
		http.MethodPost,
		"http://localhost:8000/api/v1/write/msgpack",
		bytes.NewReader(data),
	)
	if err != nil {
		log.Fatal(err)
	}
	req.Header.Set("Authorization", "Bearer "+os.Getenv("ARC_TOKEN"))
	req.Header.Set("Content-Type", "application/msgpack")
	req.Header.Set("x-arc-database", "metrics")

	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		log.Fatal(err)
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusNoContent {
		body, _ := io.ReadAll(resp.Body)
		log.Fatal(fmt.Errorf("write failed: %s: %s", resp.Status, body))
	}
}
```

For sustained ingestion, batch multiple rows per request. Arc also accepts `gzip` and `zstd` request compression through the `Content-Encoding` header.

### Binary values

Since v27.01.1, a MessagePack `bin` value (Python `bytes`, Go `[]byte`, Node `Buffer`) is stored byte for byte as a binary column (`BLOB` in SQL). Use it for a geometry as WKB, a hash, or any small opaque payload. A `null` stays NULL, and an empty value stays an empty value. Earlier versions refused the write.

```python
payload = {
    "m": "places",
    "columns": {
        "time": [now],
        "name": ["depot"],
        # WKB for POINT(-58.38 -34.60)
        "geom": [bytes.fromhex("0101000000713d0ad7a3304dc0cdcccccccc4c41c0")],
    },
}
```

Encode with `use_bin_type=True` in Python, as above, so bytes are sent as `bin` and not as a string.

**A column is either string or binary.** A write that sends bytes to a column already stored as a string, or a string to a binary column, is refused with `400` and nothing of the request is written. A column that is a string in some files and binary in others reads back as binary everywhere, so the stored strings would stop answering string functions such as `LIKE`. Arc checks against the measurement's [field schema](/arc/guides/field-schema/), so the check is best-effort: it does not run with `query.stable_schema = false`, for a column whose first values are still buffered, on a node that has not flushed or queried the measurement since it started, or between two writers changing the same column at the same moment. A change that gets through leaves the column mixed for good.

Query results show binary values as base64 in JSON and as bytes in Arrow and MessagePack; see [Querying](/arc/guides/querying/#json-query). The [spatial guide](/arc/guides/spatial/) reads WKB columns with `ST_GeomFromWKB`.

## Line protocol

Line protocol is convenient for scripts and tools that already speak the InfluxDB protocol:

```text
measurement,tag=value field=value timestamp
```

This example writes a floating-point field, an integer field, and a nanosecond timestamp:

```text
cpu,host=server01,region=us-east usage=45.2,requests=12i 1788973200000000000
```

Send it to Arc's native `POST /api/v1/write/line-protocol` endpoint.

  --header "x-arc-database: metrics" \
  --data-binary "cpu,host=server01,region=us-east usage=45.2,requests=12i $(date +%s)000000000"

### Partial writes

A line-protocol request, or a MessagePack request in [row format](/arc/api-reference/overview/#post-apiv1writemsgpack), is written point by point: a point that cannot be stored is dropped, the other points in the request are written, and the response is `400` with `partial write: N points dropped: ...`, naming each measurement, column and reason (v27.01.1+, as InfluxDB does). A point is dropped when:

- **It has a tag or field named `time`.** `time` is the timestamp, not a tag or field key (arc#1297). Before, a `time` field silently replaced the point's timestamp.
- **A value does not fit its column's type.** A column takes the type of its first value in the request. A later string in a float column, a number in a tag column, or an unsigned value above the int64 range, `NaN` or `Inf` in an integer column drops that point; an integer in a float column is widened, and a float in an integer column is truncated. Before, such a value failed the whole measurement's write with a `500` (arc#1299).
- **Two of its keys land in one column.** A field named like one of the point's tags is stored as `<name>_value`, so a point with a tag `host`, a field `host` and a field `host_value` gives one column two values.
- **Its measurement is refused for its content while the request is written.** A column that another write changed between string and binary after the request was checked, or a column name that cannot be stored, drops that measurement's points; the other measurements are written (v27.01.1+). Before, the request stopped there with a `400` that read as if nothing had been written.

#### A write that stops part-way

A request with several measurements is buffered one measurement at a time (a MessagePack batch, one record at a time). If a later one fails after earlier ones were buffered (schema churn on the measurement, a node shutting down, a WAL entry that could not be made durable), Arc answers `500` with what was written (v27.01.1+):

```json
{
  "error": "write stopped part-way at measurement \"mem\": ... Resending the whole request writes the written rows again",
  "rows_written": 120,
  "written_measurements": ["cpu", "disk"],
  "stopped_at_measurement": "mem"
}
```

`points_dropped` and `dropped` are added when points were also left out for good. The answer has no `Retry-After` and no `X-Arc-Ingest-*` header: those mean nothing was written. The measurements not in `written_measurements` were not stored, so resend only those. Telegraf and the InfluxDB clients resend the whole request on any `5xx`, which stores the written measurements twice; compaction collapses rows identical in every column, so timestamped lines converge, but lines without a timestamp get a new time on the resend and stay duplicated. Before v27.01.1 such a request was answered `503` with `Retry-After`, as if nothing had been written. A failure before anything was buffered keeps its usual answer.

Arc logs each request's drops at Error level (`Line protocol points dropped (partial write)`, or `MessagePack points dropped (partial write)`), one line per measurement, column and reason (up to 10 per request). Before v27.01.1, a row-format MessagePack point of the wrong type failed its whole measurement with a `500`, and some points with two keys in one column were accepted and then made every flush of their buffer fail.

## Verify the write

Query the measurement with arcli:

```bash
arcli query --database metrics "SELECT * FROM cpu ORDER BY time DESC LIMIT 10"
```

The `--database metrics` option sends `x-arc-database: metrics`, so the SQL only needs the measurement name: `FROM cpu`.

Arc buffers writes briefly, so newly accepted data may take a few seconds to appear in a query.

### Wait until the rows are visible (v27.01.1+)

A client that writes and then reads at once, such as a test, an agent's memory or a job step, can ask the write to answer only once its rows are visible, instead of sleeping or polling. Turn it on with `ingest.wait_visible_enabled = true` (`ARC_INGEST_WAIT_VISIBLE_ENABLED`, default `false`), then send `x-arc-wait: visible` on `/api/v1/write/msgpack` or `/api/v1/write/line-protocol`:

```bash
curl -i -X POST "http://localhost:8000/api/v1/write/line-protocol" \
  -H "Authorization: Bearer $ARC_TOKEN" \
  -H "x-arc-database: metrics" \
  -H "x-arc-wait: visible" \
  --data-binary "cpu,host=server01 usage_idle=95.2"
```

The measurements the write touched are flushed early, at most once per `ingest.wait_visible_min_interval_ms` per measurement and only while the flush pipeline has spare capacity. Otherwise the write waits for its rows' normal age or size flush, up to `max_buffer_age_ms` (5 s by default) plus the flush time. Either way it waits at most 20 s.

- **`ingest.wait_visible_min_interval_ms`** (`ARC_INGEST_WAIT_VISIBLE_MIN_INTERVAL_MS`, default `5000`, between `1000` and `3600000`; any other value stops Arc at startup). A measurement idle for longer than the interval is flushed right after the write is buffered. With the interval at most `max_buffer_age_ms`, a writer that keeps one measurement busy gets an early flush at most once per interval and waits about half the interval on average; above the age, the age flush comes first.
- **Spare capacity:** the flush queue under half full, no flush deferred within the last `max_buffer_age_ms` (at least 1 s), buffered bytes under half of `max_buffered_bytes` (when set), and at most `max(1, flush_workers / 4)` early flushes at once. A request flushes early only the measurements it wrote. A write that cannot flush early is not refused: it waits for the age flush. One request writing many measurements can hold all of the node's early-flush slots for a while.
- **Files:** an early flush writes a file like an age flush. A measurement gets at most 3 600 000 / interval (in ms) early flushes an hour, 720 at the default; overall at most `max_buffer_age_ms` / interval times the files of the age flush alone (no more at the defaults, five times as many at the 1 s floor with the default age).
- **Where:** standalone with local storage only. On object storage the write is not flushed early and ends as `202 storage_not_confirmable`.

The answers:

| Status | Headers | Meaning |
|---|---|---|
| `204` | `X-Arc-Visible: true` | Every row is in a stored file (registered too, with tiered storage). A query over HTTP `/api/v1/query` on this node that starts after the answer sees them; Flight SQL is not covered. |
| `202` | `X-Arc-Visible: false`, `X-Arc-Visible-Reason` | The rows were accepted, as a plain `204` says, but are not known to be visible. Do not resend them. The body is `{"visible": false, "reason": ..., "rows_written": ...}`. |
| `500` | `X-Arc-Visible-Reason: flush_failed_rows_at_risk` | A flush holding rows without a WAL copy failed. The body has `rows_at_risk`; the rows may still be stored, so check before resending. |

The `202` reasons:

- `timeout`: 20 s passed first.
- `shutdown`: the server began shutting down; the rows are still flushed at close.
- `flush_failed_wal_replay`: the flush failed and a WAL copy was accepted; recovery replays it. With `wal.sync_mode = "async"` that copy may not have reached the disk yet.
- `not_confirmed`: a tiering registration failed, or the rows did not all add up.
- `storage_not_confirmable`: the storage backend is S3, MinIO, GCS or Azure. Only local storage confirms in this version, and Arc logs a warning at startup.
- `future_stamped`: a row is stamped more than `query.file_time_pruning_margin_seconds` ahead in the current hour, which file-level time pruning can hide until the hour closes.

Answered at once, without waiting: a partial write (`400`) carries `X-Arc-Visible: false` and `partial_write`; a write stopped part-way (`500`) carries `write_stopped`; an empty MessagePack write keeps its `204`, with `X-Arc-Visible: true`. Refused with nothing written:

- the key off: `403`;
- another value of the header, or a cluster (`cluster.enabled`): `400`;
- the header on `/write`, `/api/v2/write`, Prometheus remote write, TLE, or an import (`/api/v1/import/csv`, `parquet`, `lp`, `tle`): `400`;
- more than 1024 waiting writes on the node: `503` with `X-Arc-Ingest-Refused: wait_visible_busy` and `Retry-After: 5`. The limit is shared by every client on the node.

Other routes ignore the header and answer without `X-Arc-Visible`; its absence never means visible. Proxies and load balancers in front of Arc need idle timeouts above 20 s. Waited writes are counted by `arc_ingest_wait_visible_total{outcome}`, `arc_ingest_wait_visible_waiters` and `arc_ingest_wait_visible_seconds`, and are left out of `arc_http_*` latency.
