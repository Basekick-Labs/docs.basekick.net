Arc runs a full analytical SQL engine over data stored as Parquet files, so window functions, CTEs, and joins are all available.

## SQL syntax

Select the database with the `x-arc-database` request header, then use the measurement name directly in SQL:

```sql
SELECT * FROM cpu LIMIT 10
```

```bash
curl --request POST http://localhost:8000/api/v1/query \
  --header "Authorization: Bearer $ARC_TOKEN" \
  --header "Content-Type: application/json" \
  --header "x-arc-database: mydb" \
  --data '{"sql": "SELECT * FROM cpu LIMIT 10", "format": "json"}'
```

This is the recommended pattern for queries within one database. The SQL examples on this page assume this header:

```http
x-arc-database: default
```

### Qualified names and the database header

A query can name its database in one of two ways, and they cannot be combined:

- **Header**: send `x-arc-database: <database>` and write bare measurement names (`FROM cpu`).
- **Qualified name**: send no `x-arc-database` header and write `database.measurement` (`FROM mydb.cpu`). This is the only way to read more than one database in a single query.

When the header is set, any `database.measurement` reference after `FROM` or `JOIN`, or in a comma-separated `FROM` list, is rejected with `400 Bad Request` before the query runs, with this error:

```text
Cross-database queries (db.table syntax) not allowed when x-arc-database header is set
```

The rule applies to `POST /api/v1/query`, `/api/v1/query/arrow`, `/api/v1/query/msgpack` and `/api/v1/query/estimate`. Clients that send the header by default need bare names: the [Python SDK](/arc/sdks/python/querying/#sql-syntax) sends it unless the client is created with `database=""`, and the [Grafana data source](/arc/integrations/grafana/#referring-to-tables) always sends it.

With neither a header nor a qualified name, a bare measurement name resolves against the `default` database.

## Query endpoints

| Endpoint | Response Format | Best For |
|----------|----------------|----------|
| `POST /api/v1/query` | JSON | Small results, debugging, dashboards |
| `POST /api/v1/query/arrow` | Apache Arrow IPC | Large result sets |
| `POST /api/v1/query/msgpack` | MessagePack (columnar) | Binary results with per-column types, `SHOW` statements |
| `GET /api/v1/query/:measurement` | JSON | Quick measurement queries |

### JSON query

```bash
curl -X POST "http://localhost:8000/api/v1/query" \
  -H "Authorization: Bearer $ARC_TOKEN" \
  -H "Content-Type: application/json" \
  -H "x-arc-database: default" \
  -d '{"sql": "SELECT * FROM cpu WHERE time > NOW() - INTERVAL '\''1 hour'\'' LIMIT 100"}'
```

JSON has no byte type, so since v27.01.1 a `BLOB` or `GEOMETRY` value is a standard base64 string (RFC 4648, padded) and a `UUID` is its canonical text (`6f1c2c1e-8a3b-4d2e-9f00-1234567890ab`). Before v27.01.1 they were raw bytes inside a JSON string, which is invalid JSON for most binary values. Arrow and MessagePack results carry real bytes. For a readable geometry use `ST_AsText(geom)` or `ST_AsGeoJSON(geom)`.

### Arrow query

For large result sets, Arrow IPC provides ~2x throughput vs JSON:

```bash
curl -X POST "http://localhost:8000/api/v1/query/arrow" \
  -H "Authorization: Bearer $ARC_TOKEN" \
  -H "Content-Type: application/json" \
  -H "x-arc-database: default" \
  -d '{"sql": "SELECT * FROM cpu LIMIT 1000000"}' \
  -o results.arrow
```

## Read every acknowledged write (v27.01.1+)

Arc acknowledges a write once its rows are buffered, and a query sees them only after their flush, up to `ingest.max_buffer_age_ms` (5 s by default) later. A reader that must see everything already acknowledged, including rows written by other clients, can ask the query to flush the measurements it reads first, instead of sleeping or polling. Turn it on with `query.fresh_flush_enabled = true` (`ARC_QUERY_FRESH_FLUSH_ENABLED`, default `false`), then send `x-arc-freshness: flush` on `/api/v1/query` or `/api/v1/query/msgpack`:

```bash
curl -i -X POST "http://localhost:8000/api/v1/query" \
  -H "Authorization: Bearer $ARC_TOKEN" \
  -H "Content-Type: application/json" \
  -H "x-arc-database: metrics" \
  -H "x-arc-freshness: flush" \
  -d '{"sql": "SELECT count(*) FROM cpu"}'
```

`$ARC_TOKEN` holds a token that can read the database; see [Creating tokens](/arc/configuration/authentication/#creating-tokens) to issue one. Arc flushes the measurements the query reads, waits until those flushes are stored, and then runs the query unchanged. A query that reads no measurement, or only measurements with nothing buffered and no flush in progress, does not wait. To make a write wait for its own rows instead, see `x-arc-wait: visible` in the [writing guide](/arc/guides/writing-data/).

With the key off, nothing changes: a query carrying the header is refused with `403`, as before.

### A flushed answer

A query that ran answers `200` with `X-Arc-Freshness: flushed` and `X-Arc-Freshness-Wait-Ms: <ms>`, the time it waited. Every row this node acknowledged before the request arrived, in a measurement the query reads, was in a stored Parquet file before the query's SQL was built, with two exceptions:

- Rows without a WAL copy that were never stored: their flush failed, or Arc stopped before it ran (a crash, or a shutdown that ran out of time). A row has no WAL copy when the WAL is off, when it was dropped under WAL backpressure in queued ack mode, when its asynchronous WAL write failed, or when that write had not completed when Arc stopped.
- Rows in a WAL file that recovery quarantined, logged at Error and counted in `arc_wal_quarantined_files_total`.

If acknowledged rows must survive a crash, turn the [WAL](/arc/advanced/wal/) on with `wal.ack_mode = durable`. As for any query, file-level time pruning can leave out rows stamped more than `query.file_time_pruning_margin_seconds` ahead of the server clock, in the current hour, until the hour closes. A later DELETE or retention run can remove rows after the answer.

For a query that ran, `execution_time_ms` and the query latency metrics start after the wait; a refusal's `execution_time_ms` includes it.

### Refusals

Any other answer carries `X-Arc-Freshness: false` and `X-Arc-Freshness-Reason: <reason>`, and the query is not run:

| Reason | Status | When |
|---|---|---|
| `invalid_value` | `400` | Any value other than `flush` (in any case). Every value of a repeated header is read; empty values count as absent. |
| `disabled` | `403` | `query.fresh_flush_enabled` is off, on every query route. |
| `unsupported_route` | `400` | The key is on and the route is `/api/v1/query/arrow`, `/api/v1/query/estimate` or `/api/v1/query/:measurement`. |
| `cluster` | `400` | `cluster.enabled`, before any forward. |
| `storage_not_supported` | `400` | S3, MinIO, GCS or Azure storage, or a local volume that folds names. |
| `tiering_not_supported` | `400` | Tiered storage is active (enabled and licensed). |
| `show_not_supported` | `400` | `SHOW DATABASES`, `SHOW TABLES`. |
| `forbidden` | `403` | RBAC denies a measurement the query reads. Nothing is flushed. |
| `too_many_measurements` | `400` | The query reads more than 64 measurements. |
| `busy` | `503`, `Retry-After: 5` | More than `query.fresh_flush_max_waiters` fresh queries are waiting on the node. |
| `flush_failed_wal_replay` | `503`, `Retry-After` | WAL on: an earlier flush failed and its rows wait for WAL recovery. `Retry-After` is `wal.recovery_interval_seconds`, at most 3600. |
| `recovery_pending` | `503`, `Retry-After` | WAL on: a recovery pass left files to replay. |
| `flush_failed` | `503` | A flush the query waited for failed. |
| `not_confirmed` | `503` | A flush the query waited for ended without a confirmed store. |
| `timeout` | `504` | 30 s, or the query's own timeout if sooner (`query.timeout`, or the token's governance time limit), passed during the wait. |
| `shutdown` | `503` | The server began shutting down during the wait. |
| `cancelled` | `503` | The client disconnected during the wait (with `query.cancel_on_client_disconnect`). |
| `fresh_flush_unavailable` | `503` | The buffer cannot wait for flushes. This is a configuration fault, logged at Error. |
| `query_error` | the query's own | Any other error before or after the wait: an invalid body or SQL, governance, a failed execution. |

The refusals from `invalid_value` to `tiering_not_supported` come before the query is counted in `arc_query_requests_total`. The others count there and in `arc_query_errors_total` (`busy` too, like a governance `429`), and `timeout` also counts in `arc_query_timeouts_total` when the query's own timeout was what passed. A panic is answered `500` with `query_error`. An error inside a stream that already started with `200` is the query's own, and its rows were flushed.

The checks run after authentication. Flight SQL refuses the header with `InvalidArgument` for any non-empty value, with the feature on or off. The absence of `X-Arc-Freshness` never means fresh.

### Latency and limits

A fresh query buys the guarantee, not lower latency. A measurement is flushed early at most once per `query.fresh_flush_min_interval_ms`, and only while the flush pipeline has spare capacity: fewer than `max(1, ingest.flush_queue_size / 2)` flushes queued (rounded down, so a queue of 1 must be empty), no flush deferred within the last `ingest.max_buffer_age_ms` (at least 1 s), buffered bytes under half of `ingest.max_buffered_bytes` (when set), and at most `max(1, ingest.flush_workers / 4)` early flushes at once. That capacity, and each measurement's record of its last flush, are shared with writes sent with `x-arc-wait: visible`: an early flush from either makes the measurement not due for the other.

- A fresh query on a measurement written continuously waits for its next flush, up to the interval.
- A query that cannot flush a measurement early (no spare capacity) waits for that measurement's age or size flush, up to `ingest.max_buffer_age_ms`.
- One fresh query over more measurements than the early-flush slots (`max(1, ingest.flush_workers / 4)`) flushes the first ones early and waits for the age flush of the rest.
- The wait lasts at most 30 s, or less if the query's own timeout comes first. Proxies and load balancers in front of Arc need idle timeouts above 30 s.

Configuration keys, in the `[query]` section:

- **`query.fresh_flush_enabled`** (`ARC_QUERY_FRESH_FLUSH_ENABLED`, default `false`). Off, the header is refused with `403`.
- **`query.fresh_flush_min_interval_ms`** (`ARC_QUERY_FRESH_FLUSH_MIN_INTERVAL_MS`, default `5000`, between `1000` and `3600000`; any other value stops Arc at startup). How often a fresh query may flush one measurement early.
- **`query.fresh_flush_max_waiters`** (`ARC_QUERY_FRESH_FLUSH_MAX_WAITERS`, default `64`, between `1` and `1024`). The fresh queries waiting on the node at once; one more is refused with `503 busy`. The limit is per node and shared by every client: one token can hold every slot for up to 30 s. A disconnected client's slot is released within a quarter second, unless `query.cancel_on_client_disconnect = false`, when it is held to the end of the wait. A waiting fresh query is not listed in `/api/v1/queries` and cannot be cancelled there until its wait ends; only a client disconnect ends it early.

Also:

- **Where:** standalone with local storage, on `/api/v1/query` and `/api/v1/query/msgpack` only. A cluster, object storage and active tiered storage refuse the header with `400`.
- **Files:** an early flush writes a file like an age flush, at most 3 600 000 / interval (in ms) per measurement an hour, 720 at the default.
- **Security:** a read token can make Arc flush the measurements it can read, at most once per interval each, inside the spare capacity and the waiter limit. With auth off, any client can.
- **Load warnings:** Arc logs a warning at startup when the key is on with a cluster, object storage or tiered storage enabled (where the header is refused), with `ingest.max_buffer_age_ms` above 15000 or at least `query.timeout` (a query that falls back to the age flush can end `504`), and with `query.fresh_flush_min_interval_ms` above `ingest.max_buffer_age_ms`.
- **Browsers:** the header may be sent cross-origin (CORS), and the three answer headers are exposed.
- **Cost:** without the header, a query pays one header lookup. With the key on, every flush on the node also records its measurement's flush time and is tracked until it is stored, which costs one more small lock per flush; this applies even where tiered storage refuses the header. A fresh query transforms its SQL twice, once to learn the measurements it reads and once after the wait.

Fresh queries are counted by `arc_query_fresh_flush_total{outcome}`, `arc_query_fresh_flush_waiters` and `arc_query_fresh_flush_seconds`, and are left out of `arc_http_*` latency; `arc_ingest_forced_flushes_total{source="read"}` counts the early flushes they asked for. See [Monitoring](/arc/operations/monitoring/#query-latency-and-errors).

## Time filtering

Arc stores timestamps in the `time` column. Use standard SQL intervals for time-range queries:

```sql
-- Last hour
SELECT * FROM cpu
WHERE time > NOW() - INTERVAL '1 hour';

-- Last 7 days
SELECT * FROM cpu
WHERE time > NOW() - INTERVAL '7 days';

-- Specific date range
SELECT * FROM cpu
WHERE time BETWEEN '2026-01-01' AND '2026-01-31';
```

<Callout type="idea" title="Partition Pruning">
Time-range filters using the `time` column automatically trigger partition pruning, skipping Parquet files outside the range. Always include a time filter for best performance.
</Callout>

## Time-series aggregation

### time_bucket

Group data into fixed-size time intervals:

```sql
-- Hourly averages for the last 7 days
SELECT
  time_bucket('1 hour', time) AS bucket,
  AVG(cpu_usage) AS avg_cpu,
  MAX(cpu_usage) AS max_cpu,
  COUNT(*) AS samples
FROM cpu
WHERE time > NOW() - INTERVAL '7 days'
GROUP BY bucket
ORDER BY bucket;
```

### date_trunc

Truncate timestamps to calendar boundaries:

```sql
-- Daily summary for the last 30 days
SELECT
  date_trunc('day', time) AS day,
  host,
  AVG(cpu_usage) AS avg_cpu,
  AVG(mem_usage) AS avg_mem
FROM cpu
WHERE time > NOW() - INTERVAL '30 days'
GROUP BY day, host
ORDER BY day DESC, host;
```

## Window functions

Compute rolling metrics and detect anomalies:

```sql
-- 10-minute moving average with anomaly detection
SELECT
  time,
  host,
  cpu_usage,
  AVG(cpu_usage) OVER (
    PARTITION BY host
    ORDER BY time
    ROWS BETWEEN 10 PRECEDING AND CURRENT ROW
  ) AS moving_avg,
  cpu_usage - AVG(cpu_usage) OVER (
    PARTITION BY host
    ORDER BY time
    ROWS BETWEEN 60 PRECEDING AND CURRENT ROW
  ) AS deviation
FROM cpu
WHERE time > NOW() - INTERVAL '1 hour';
```

## Common table expressions (CTEs)

Break complex queries into readable steps:

```sql
-- Find hosts with anomalous CPU spikes
WITH hourly_stats AS (
  SELECT
    host,
    time_bucket('1 hour', time) AS bucket,
    AVG(cpu_usage) AS avg_cpu,
    STDDEV(cpu_usage) AS std_cpu
  FROM cpu
  WHERE time > NOW() - INTERVAL '24 hours'
  GROUP BY host, bucket
),
anomalies AS (
  SELECT *
  FROM hourly_stats
  WHERE avg_cpu > 80 OR std_cpu > 20
)
SELECT host, bucket, avg_cpu, std_cpu
FROM anomalies
ORDER BY avg_cpu DESC;
```

## Cross-database queries

To join measurements in different databases, qualify every name with its database and send the request **without** the `x-arc-database` header:

```bash
curl -X POST "http://localhost:8000/api/v1/query" \
  -H "Authorization: Bearer $ARC_TOKEN" \
  -H "Content-Type: application/json" \
  -d @- <<'JSON'
{"sql": "SELECT c.time, c.host, c.cpu_usage, d.version FROM production.cpu c JOIN ops.deployments d ON c.host = d.host AND c.time BETWEEN d.time AND d.time + INTERVAL '1 hour' WHERE c.time > NOW() - INTERVAL '24 hours'"}
JSON
```

The same query, formatted:

```sql
-- Join CPU metrics in "production" with deployment events in "ops"
SELECT
  c.time,
  c.host,
  c.cpu_usage,
  d.version
FROM production.cpu c
JOIN ops.deployments d
  ON c.host = d.host
  AND c.time BETWEEN d.time AND d.time + INTERVAL '1 hour'
WHERE c.time > NOW() - INTERVAL '24 hours';
```

A comma-separated `FROM` list follows the same rule as `JOIN`: qualified names only without the header, bare names with it. This self-join uses bare names, so it runs with the header:

```sql
SELECT count(*)
FROM otel_logs a, otel_logs b
WHERE a.TraceId = b.TraceId AND a.TraceId <> '';
```

## Useful SQL functions

These are the functions most useful for analytical and time-series queries:

| Function | Description | Example |
|----------|-------------|---------|
| `NOW()` | Current timestamp | `WHERE time > NOW() - INTERVAL '1h'` |
| `time_bucket(interval, time)` | Fixed-size time buckets | `time_bucket('5 minutes', time)` |
| `date_trunc(part, time)` | Calendar truncation | `date_trunc('day', time)` |
| `epoch(time)` | Timestamp to epoch seconds | `epoch(time)` |
| `PERCENTILE_CONT(p)` | Percentile (continuous) | `PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY latency)` |
| `APPROX_QUANTILE(col, p)` | Approximate percentile (faster) | `APPROX_QUANTILE(latency, 0.99)` |
| `STDDEV(col)` | Standard deviation | `STDDEV(cpu_usage)` |
| `LAG(col) OVER (...)` | Previous row value | `LAG(value) OVER (ORDER BY time)` |
| `LEAD(col) OVER (...)` | Next row value | `LEAD(value) OVER (ORDER BY time)` |

## Aggregate functions

Arc supports the **full analytical SQL aggregate set** — there is no allowlist. Beyond the standard `COUNT`/`SUM`/`AVG`/`MIN`/`MAX`, the following are commonly useful for analytics:

| Function | Description | Example |
|----------|-------------|---------|
| `COUNT(DISTINCT col)` | Distinct count | `COUNT(DISTINCT host)` |
| `APPROX_COUNT_DISTINCT(col)` | Fast approximate distinct count | `APPROX_COUNT_DISTINCT(user_id)` |
| `MEDIAN(col)` | Median value | `MEDIAN(latency)` |
| `MODE(col)` | Most frequent value | `MODE(status_code)` |
| `QUANTILE_CONT(col, p)` | Continuous quantile | `QUANTILE_CONT(latency, 0.95)` |
| `STDDEV(col)` / `VARIANCE(col)` | Standard deviation / variance | `STDDEV(cpu_usage)` |
| `ARG_MAX(arg, val)` / `ARG_MIN(arg, val)` | `arg` at the row where `val` is max/min | `ARG_MAX(host, cpu_usage)` |
| `FIRST(col)` / `LAST(col)` | First / last value in group | `LAST(value)` |
| `STRING_AGG(col, sep)` | Concatenate values | `STRING_AGG(host, ', ')` |
| `LIST(col)` / `ARRAY_AGG(col)` | Collect values into a list | `LIST(value)` |
| `HISTOGRAM(col)` | Value-count map | `HISTOGRAM(status_code)` |
| `CORR(y, x)` | Correlation coefficient | `CORR(cpu_usage, mem_usage)` |
| `REGR_SLOPE(y, x)` / `REGR_INTERCEPT(y, x)` | Linear regression slope / intercept | `REGR_SLOPE(value, epoch(time))` |
| `ENTROPY(col)` | Shannon entropy | `ENTROPY(status_code)` |

This is a selection, not the full set. There is no allowlist — if a standard analytical aggregate exists, Arc accepts it. An unrecognised function returns a query error naming it, so trying one is safe.

## Performance tips

1. **Always filter by time** -- Partition pruning skips entire Parquet files outside the range, often by a wide margin.

2. **Use Arrow for large results** -- Arrow IPC provides ~2x throughput vs JSON for result sets over 100K rows.

3. **Limit result sets** -- Add `LIMIT` when exploring data. Scanning millions of rows without a limit is expensive.

4. **Use aggregations server-side** -- Compute `AVG`, `COUNT`, `SUM` in SQL rather than fetching raw rows and aggregating client-side.

5. **Prefer `APPROX_QUANTILE` over `PERCENTILE_CONT`** -- For large datasets, approximate percentiles are substantially faster.

6. **Use `time_bucket` over `date_trunc`** -- `time_bucket` supports arbitrary intervals (5 min, 15 min, 4 hours) while `date_trunc` is limited to calendar boundaries.
